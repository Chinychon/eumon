Architecture

How Eumon runs: one Cloudflare Worker checks who is asking, then serves the dashboard, the API, the public landing pages and the background Workflows, on top of a stack of TypeScript packages. Read this before changing bindings, adding a route, or moving code between packages.

One Worker does everything

There is a single deployable: the apps/web workspace (@organic-growth/web), deployed as the Worker named eumon. The same Worker:

  • renders the dashboard at /, the sign-in page, invitation links and /admin,
  • answers Better Auth's sign-in endpoints under /api/auth/*,
  • answers the JSON API under /api/*,
  • serves published landing pages under /p/<siteId>/… and the client share link under /r/<token>,
  • runs the daily cron trigger,
  • and hosts the three Workflow classes that do long work (analysis, data collection, Results sync).

There is no separate API server, queue consumer or second Worker. The older diagram at docs/architecture.html shows the same system from an earlier point; this page is the current description.

Build and serve

The app is written with the Next.js App Router conventions (app/page.tsx, app/layout.tsx, app/**/route.ts) but is built by vinext, a Vite-based implementation of those conventions, not by Next.js. apps/web/vite.config.ts loads two plugins: vinext() and @cloudflare/vite-plugin with remoteBindings: false and the rsc environment (with ssr as a child).

Worker settings and bindings
apps/web/cloudflare.config.ts, written with the cf/config helpers (defineWorker, bindings, triggers, exports). There is no wrangler.jsonc. The AppEnv type is inferred from this file, so a binding added here is typed everywhere.
Worker entry
apps/web/worker.ts (the entrypoint in the config). Its fetch checks every request before handing it to vinext's fetch handler (see How a request flows). It also re-exports the three Workflow classes and adds the scheduled handler.
Compatibility
compatibilityDate: "2026-10-05", flag nodejs_compat.
Preview URLs
previewUrls: false (apps/web/cloudflare.config.ts:9), so preview hostnames don't serve the app. The workers.dev address is not turned off; the sign-in gate protects it like any other hostname.
Static files
apps/web/public/, served through the ASSETS binding with notFoundHandling: "none".
Dev server
vite dev --port 5174 --strictPort. The predev script (apps/web/scripts/predev.mjs) rebuilds the shared packages and applies pending local migrations first.
Deploy
vinext-cloudflare deploy (the CLI from @vinext/cloudflare), run by npm run deploy in apps/web. See Operating it.

Route code reads bindings with import { env } from "cloudflare:workers" rather than from a handler argument. Workflow classes read them from this.env.

The web app imports the shared packages' built output, not their sources. After editing anything in packages/*, run npm run build:packages (or restart npm run dev, which does it) or the app keeps running the old code.

Cloudflare has no optional secrets: every secret declared in cloudflare.config.ts must be set on the Worker before a deploy. That is why ANTHROPIC_API_KEY and LLM_MODEL are deliberately left out of the config. Set them with wrangler secret put in production; to use them in local dev, declare them in the config again. Keep settings in the config and not in the Cloudflare dashboard, or a Workers Builds deploy (strict mode) aborts on the difference. See Gotchas.

remoteBindings is false in vite.config.ts, so the AI binding does not work in local dev. Set DEEPSEEK_API_KEY or ANTHROPIC_API_KEY in apps/web/.dev.vars to use the AI steps locally.

How a request flows

Every request reaches the fetch handler in apps/web/worker.ts:31 before vinext sees it. In order:

  1. Sign-in endpoints. Paths under /api/auth/ go to Better Auth (apps/web/worker.ts:33). Anything but a GET first takes one token from AUTH_RATE_LIMIT, keyed on the cf-connecting-ip header, and answers 429 when the bucket is empty. Better Auth's endpoints that list a workspace's people (apps/web/src/auth-paths.ts:2) only check membership, so the Worker refuses them with 403 for a Client of any workspace the request could name (apps/web/worker.ts:18).
  2. Session. For any other path that is not public, the Worker reads the session with authFor(env).api.getSession. Public paths skip this, so landing pages, the beacon and conversion events never touch the auth tables (apps/web/worker.ts:44).
  3. The gate. gate(request, signedIn) (apps/web/src/gate.ts:21) lets public paths through. Without a session, /api/* answers 401 and a page redirects (303) to /sign-in?next=…. With a session, a write to /api/* (any method but GET, HEAD, OPTIONS) whose Origin header is not the app's own origin answers 403, because the session cookie travels on cross-site requests too.
  4. The route. vinext runs the page or route handler (How requests are handled). Each API handler calls a guard that checks the caller's role (Route guards and limits).
  5. Headers. The response gets the app's security headers, except under /p/, where landing pages set their own (apps/web/worker.ts:49; see Security headers).

The public paths are a list of patterns in apps/web/src/gate.ts:7: landing pages (/p/), conversion events, client Results links (/r/, /api/r/), log ingest (/api/logs/), Better Auth, /sign-in, /invite/ and the static files. The public API routes check what they can on their own: client links need a signed token, log ingest a per-site token, and conversion events an Origin on the site's own domain. Everything else needs a session, so a route someone forgets to guard is still not public. The full list and what each path is for: Web app: access control.

A new public path needs an entry in apps/web/src/gate.ts:7 and, for an API route, in the PUBLIC set of apps/web/src/routes-guarded.test.ts:7. Otherwise the gate turns it into a sign-in redirect, or the test fails because the handler calls no guard.

Sign-in: Better Auth

Accounts, sessions and workspaces come from Better Auth, configured in apps/web/src/auth.ts. A workspace is a Better Auth organization.

One instance per isolate
authFor(env) (apps/web/src/auth.ts:132) builds the instance with createAuth(env) on first use and reuses it, since env is fixed for an isolate's lifetime.
Storage
D1, through database: env.DB (apps/web/src/auth.ts:51). Migration 0024_accounts.sql creates Better Auth's tables (user, session, account, verification, organization, member, invitation, with Better Auth's camelCase columns) and Eumon's own: site_access, site_access_invites, workspace_limits, workspace_usage, workspace_github_installations, plus sites.workspace_id and sites.log_token. See Data model.
Methods
Google, through the same GOOGLE_CLIENT_ID as the Search Console connection, with includeGrantedScopes: false so sign-in tokens stay sign-in scoped (apps/web/src/auth.ts:63). Its redirect URI is /api/auth/callback/google. Magic links need EMAIL_ENABLED; email with password needs PASSWORD_SIGNIN as well (apps/web/src/auth.ts:26). Passwords hash with WebCrypto PBKDF2 (apps/web/src/passwords.ts), which still exceeds the Free plan's CPU limit.
Turnstile
Better Auth's captcha plugin checks a Turnstile token on the email endpoints: sign-up, email sign-in, magic link, password reset, verification email (apps/web/src/auth.ts:118). Google sign-in has no Turnstile check, and the sign-in page only loads the widget when an email method is on (apps/web/app/sign-in/SignInForm.tsx:38).
Rate limit
AUTH_RATE_LIMIT, applied by the Worker before Better Auth runs (apps/web/worker.ts:35).
Sessions
30 days, extended at most once a day, with a signed cookie cache of 5 minutes (apps/web/src/auth.ts:73). Most requests read the session from the cookie and touch no D1 rows, which matters on D1's free limits.
Roles
owner, member and client, built with the organization plugin's access control; client has no organization permissions (apps/web/src/auth.ts:41). Each user may own one workspace (organizationLimit calls ownsWorkspace); being a Member or Client of others doesn't count. The API cannot delete a workspace (disableOrganizationDeletion).
Invitations
Owners invite through POST /api/workspace/invitations, which returns a link to share by hand while email is off. A Client invitation lists the sites it grants; accepting copies them into site_access (apps/web/src/auth.ts:107). Everyone in the workspace (Owners included) plus pending invitations count against the workspace's people limit (apps/web/src/auth.ts:101).
Bootstrap owner
Migration 0024 creates the workspace ws_initial, moves every existing site into it, and gives it no limits. A user whose verified email is in BOOTSTRAP_OWNER_EMAIL joins it as Owner when their account is created and on every new session (packages/db/src/workspaces.ts:32, packages/db/src/workspaces.ts:55). The same list decides who may open /admin.

Route guards and limits

The gate only knows whether someone is signed in. Which sites they may see, and what they may change, is checked in each API handler with one of the guards in apps/web/src/guard.ts:

GuardUse it when the route
requireSite(request, siteId, need)names a site. Returns the site and the caller's role, or a response to return. A site the caller can't see answers 404, the same as a missing one (apps/web/src/guard.ts:32).
requireOwned(request, kind, id, need)names a row that belongs to a site (an analysis, change, job, record, dataset, source, template or page). It looks up the row's site_id (apps/web/src/access.ts:26), then checks the site.
requireWorkspace(request, need)works on the active workspace: listing and adding sites, invitations, the GitHub install.
requireViewer(request)only needs a signed-in user, such as GET /api/me.
requirePlatformAdmin(request)is part of /admin. Anyone not listed in BOOTSTRAP_OWNER_EMAIL with a verified email gets 404.

need is "read", "write" or "admin", and allows(role, need) (apps/web/src/access.ts:6) decides. Owners and Members see every site in the workspace; a Client sees only sites in site_access (siteForUser, packages/db/src/index.ts:1370). apps/web/src/routes-guarded.test.ts reads every route.ts under app/api and fails if an exported handler doesn't call a guard.

Limits sit next to the guards in apps/web/src/limits.ts. Every workspace starts from FREE_LIMITS (apps/web/src/limits.ts:18), and a row in workspace_limits overrides any of them; /admin writes those rows.

  • Metered actions (analyses, scraped pages, Ask questions, AI runs) call charge once the route's own checks pass, just before the work (apps/web/src/limits.ts:43). It is one upsert into workspace_usage that only adds while the day's total stays within the limit (packages/db/src/workspaces.ts:103), so two requests at once cannot both pass the last slot. A refusal answers 429 with a sentence to show. A request refused for another reason costs nothing, and work that then can't start is given back with refund (line 50). Page views and beacons are never metered.
  • Features (DataForSEO, pull requests, Sheets export) are on or off per workspace. featureRefusal (apps/web/src/limits.ts:57) makes a route answer 403, and the Results sync drops the DataForSEO key for workspaces without it (apps/web/src/sync-steps.ts:93).
  • Counts: the site limit is checked by POST /api/sites, the people limit by Better Auth's invitation hook.

The default numbers are listed in Web app: access control.

Security headers

apps/web/src/headers.ts holds two header sets.

The app (APP_HEADERS)
X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, X-Frame-Options: DENY, and Content-Security-Policy: frame-ancestors 'none'; base-uri 'self'; object-src 'none'. The Worker adds them to every response outside /p/, including the gate's refusals and Better Auth's responses.
Landing pages (PAGE_HEADERS)
nosniff, the same referrer policy, and Content-Security-Policy: base-uri 'none'; object-src 'none'. No frame rules, because the customer's own site may frame them. Set on landing-page HTML by apps/web/src/public-pages.ts:47.

Neither policy restricts scripts (no script-src). vinext streams the React Server Components payload as inline <script> tags, and the landing-page beacon is an inline script with per-page config (packages/pages/src/render.ts:142). A script policy would need a per-request nonce threaded through both renderers. Until then, HTML escaping in the renderers is the defence against injected scripts, so keep every value escaped.

The cron trigger

The config declares one trigger, triggers.scheduled({ schedule: "15 4 * * *" }): every day at 04:15 UTC (apps/web/cloudflare.config.ts:12). Cloudflare calls the scheduled handler in apps/web/worker.ts:52, which calls startDailySyncs (apps/web/src/sync-steps.ts:212) inside ctx.waitUntil.

  1. startDailySyncs lists every site (listSitesForResults in packages/db/src/metrics.ts:283).
  2. For each site it calls startSync with trigger: "daily", which creates a SearchSyncWorkflow instance with the ID daily-<YYYY-MM-DD>-<siteId>.
  3. Because the ID is fixed per site and day, a second firing on the same day creates nothing new.

"Sync now" in the dashboard uses the same startSync with trigger: "manual" and the ID manual-<siteId>-<10-minute window>, so repeated clicks within ten minutes join one run, and a manual sync is refused (409) while that site's daily run is in flight.

A cron trigger is used instead of Workflow schedules because schedules need the paid plan. The sync workflow runs a site's sources in one step and URL inspections in steps of 40 to stay within the Free plan's 50 subrequests per step. See Results sync flow.

How the packages layer

Shared code lives in eight workspaces under packages/, all named @organic-growth/*. The root build:packages script builds them in dependency order: core, ai, db, repo-analyzer, crawler, scraper, pages, agents.

ai@anthropic-ai/sdk onlyNetwork: DeepSeek over fetch, Anthropic through the SDK, Workers AI through the AI binding passed in.
dbcoreD1, through a small D1Like interface (packages/db/src/d1.ts). Tests run against openSqliteD1, Node's built-in SQLite with every migration applied (packages/db/src/sqlite.ts).
crawlercoreNetwork: fetches pages, sitemaps and robots.txt through an injectable fetcher.

@organic-growth/webagents, ai, core, crawler, db, pages, repo-analyzer, scraperEverything: routes, Workflows, bindings.

Every package has a test script that compiles with tsconfig.test.json and runs node --test, so all of them are tested in plain Node, not in a Worker runtime. Code that needs D1 is tested against openSqliteD1; model calls go through a JsonLlm argument, and the crawler and createLlm accept a fetcher argument. More per package in Packages.
