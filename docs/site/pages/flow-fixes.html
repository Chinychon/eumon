What it does

Eumon prepares fixes only for repositories whose fingerprint is Next.js with the App Router, and only when the workspace plan includes pull requests. Any other stack gets no fixes. The five fix types are:

  • metadata-base: sets metadataBase in the root layout (app/layout.* or src/app/layout.*, any of .tsx, .jsx, .js, .ts). Canonical and hreflang fixes wait until the layout has it; if Eumon can't find or read the root layout, it proposes neither.
  • head: adds or fixes a page's title, description, canonical URL and hreflang tags. When the root layout sets title.template, the title is written without the site name and checked for length as the template renders it. hreflang lists only the locales the page exists in; on a route under a locale segment ([locale]) it is left to a snippet, and so is a canonical that would replace hreflang set by a layout.
  • jsonld: adds structured data to a page.
  • llms-txt: creates or refreshes public/llms.txt.
  • ai-robots: allows AI search crawlers in public/robots.txt.

Fixes are staged at the end of each analysis. With Autopilot on, Eumon opens at most 3 draft pull requests per run, and never more open Eumon pull requests than the site's PR budget (1 to 5, default 3). Branches are named eumon/<kind>-<route>-<id>.

From draft to merge

  1. A pull request opens as a draft. It leaves draft only after the repository's checks pass.
  2. If the checks fail, the fix is marked failed and Eumon comments on the pull request, which stays open as a draft for you to fix, reject or close.
  3. Once the checks pass, Eumon confirms the change in the raw HTML of the preview deploy, running the same head-tag checks that found the problem. If the preview doesn't show the change, the fix is marked failed with a comment saying what is missing.
  4. If there is no usable preview (none found, password-protected, or not answering 200), Eumon marks the pull request ready on the passing build alone once 30 minutes have passed. That happens on the next GitHub event for the pull request, or within a day through the daily sweep.
  5. A person reviews and merges. Eumon never merges.
  6. Drafts and failed pull requests that haven't changed in 7 days are closed. A pull request marked ready stays open until someone merges or closes it.
  7. After a merge, the first crawl that starts after it checks the changed pages. If they broke, Eumon opens a revert pull request, but only when the files are unchanged since the merge. Otherwise it asks the user to use GitHub's Revert button.
  8. Rejected and reverted fixes are not proposed again. Nor is a fix whose pull request is still open (even a failed one), or one merged in the last 30 days.

The webhook handles check, status, deployment and pull request events as they arrive. A daily sweep from the cron trigger catches any the webhook missed: merges and closes for every open Eumon pull request, plus the checks and preview for drafts. It handles at most 4 pull requests per run, stale ones first, because of the Free plan's subrequest limits. A failed pull request still counts against the PR budget until it is closed.

What the AI writes

The model only writes words: titles, descriptions and schema field mappings, and only from facts found on the site's own pages. Anything it cannot ground is offered as a copy-paste snippet instead of a change. An analysis makes at most 30 AI calls for fixes (apps/web/src/fix-steps.ts, FIX_AI_CALLS).

What it never does

  • Merge a pull request.
  • Touch a file outside app/**/page.tsx (or src/app/...), the root layout.tsx, components/eumon-json-ld.tsx, public/llms.txt and public/robots.txt.
  • Add a dependency.
  • Allow AI training crawlers. Only OAI-SearchBot, Claude-SearchBot and PerplexityBot are allowed, and only when the site's "Let AI search crawlers read the site" setting is on.
  • Edit a hand-written llms.txt. Eumon creates or refreshes the file only when it carries the line <!-- maintained by Eumon -->.
  • Overwrite components/eumon-json-ld.tsx. It is written only if it does not exist and must match Eumon's version exactly.

GitHub App setup

The administrator of the GitHub App does this once, at github.com/settings/apps/eumon-growth-engine.

  1. Repository permissions. Contents read and write, Pull requests read and write, Checks read, Commit statuses read, Deployments read.
  2. Events. Subscribe to Check run, Check suite, Status, Deployment status and Pull request.
  3. Webhook. Set the URL to https://eumon.chin-gabriel.workers.dev/api/github/webhook and a random secret.
  4. Secret. From apps/web, run npx wrangler secret put GITHUB_WEBHOOK_SECRET and paste the same value. Locally it goes in apps/web/.dev.vars.
  5. Existing installations. Each installation must accept the new permissions before fixes work on its repositories.

Apply migration 0028_fix_engine.sql to the remote database before the deploy that includes the fix engine (see Remote migrations). It adds the fix tables and the per-site settings, including the PR budget.
