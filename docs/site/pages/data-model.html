Data model

Every table in the D1 database as it stands after the last migration, grouped by what it serves, with the functions in packages/db/src that write and read it. Read this before adding a column, a table, or a query.

Where the schema lives

The schema is the sum of the SQL files in packages/db/migrations/, applied in file-name order (0001_init.sql to 0024_accounts.sql). There is no separate schema file. Later migrations add columns, drop tables, and rebuild tables through *_new copies, so reading one early migration on its own gives a wrong picture. The tables below are the result of applying all 24: 49 tables, counted by applying every migration to an empty SQLite database.

All SQL lives in @organic-growth/db: packages/db/src/index.ts (sites, analyses, crawl, changes, search metrics) re-exports the domain modules page-engine.ts, metrics.ts, coverage.ts, snapshots.ts, activity.ts, assistant.ts, leads.ts, server-logs.ts, history.ts, search-console.ts and workspaces.ts. Every function takes a D1Like (packages/db/src/d1.ts), the subset of the D1 binding the code uses, so the same functions run against D1 in the Worker and against Node's SQLite in tests. The exceptions: the demo seeder in packages/agents/src/demo.ts writes some rows with its own SQL; Better Auth reads and writes its own tables through the D1 binding (database: env.DB, apps/web/src/auth.ts:51); resolveSiteId (apps/web/src/access.ts:26) looks up the site that owns a row; and apps/web/worker.ts:22 looks up a workspace by slug.

Ownership: everything cascades from sites

Migration 0019 (packages/db/migrations/0019_ownership_and_indexes.sql) set one rule: every table with a site_id has REFERENCES sites(id) ON DELETE CASCADE. Inside a site, ownership is narrower:

  • pages, crawl_counts and changes cascade from analyses.
  • page_metrics_daily, ai_page_daily, page_index_status and page_revisions cascade from generated_pages, which cascades from page_templates, which cascades from datasets.
  • data_sources and data_records cascade from datasets; scrape_queue from jobs; assistant_messages from assistant_threads.

The accounts tables from 0024 follow the same rule from the other side: site_access and site_access_invites cascade from sites as well as from their user or invitation; member, invitation, workspace_limits, workspace_usage and workspace_github_installations cascade from organization; session, account, member, site_access and the invitations a user sent (inviterId) cascade from user.

So deleting a site is a single DELETE FROM sites. deleteSite (packages/db/src/index.ts:96) clears page_links and the site's pages rows first, so no single statement carries the whole cascade of the two largest tables. 0019 also keyed page_sessions by (site_id, session_id): the session id comes from the browser, so one site can't claim another's.

sites.workspace_id references organization without ON DELETE CASCADE, on purpose. Deleting a workspace that still has sites fails with "FOREIGN KEY constraint failed" instead of wiping every site's data through the cascades above. This is a plain foreign key, not a trigger. Better Auth's own workspace deletion is also switched off (disableOrganizationDeletion, apps/web/src/auth.ts:95).

D1 enforces foreign keys, and so does the test shim (Node's DatabaseSync turns foreign_keys on by default). A cascade that works in tests works in production, and an insert with a missing parent fails in both.

The metric_points ledger

metric_points stores one number per site, metric and day. Results reads its time series from it.

  • Values are additive components. A point is either a daily sum (clicks, impressions, leads, page views) or the value on that day (published pages). Ratios are never stored: they are derived at read time from their parts. Search Console position, for example, is stored as search_position_weight (position times impressions) beside search_impressions, and resultsView computes CTR and average position over any window (packages/core/src/results.ts:288). That makes weekly and windowed comparisons correct by summing.
  • Writes overwrite. upsertMetricPoints (packages/db/src/metrics.ts:13) is ON CONFLICT … DO UPDATE SET value = excluded.value, so a re-run or a Search Console revision replaces a day instead of double counting.
  • Metric names are declared once in METRICS (packages/core/src/results.ts:90), grouped by the source that writes them. A group is what that source's sync may write and what a changed property clears (clearMetricPoints).

Writers: the first-party, lead-outcome and AI syncs in metrics.ts, every finished analysis (a site-health point from analysisHealthPoints), the Search Console import chart (gsc_indexed, gsc_not_indexed), and the connector syncs in apps/web/src/results-sync.ts and apps/web/src/sync-steps.ts.

Retention and pruning

A 25,000-page crawl is tens of MB and a D1 database on the Free plan holds 500 MB, so crawl rows are not kept forever.

  • Crawl rows. When an analysis finishes, saveAnalysisReport calls pruneCrawlResults (packages/db/src/index.ts:396). It deletes the pages rows of every older analysis except the latest KEPT_CRAWLS (2) finished ones and any run newer than the latest finished one, which a re-run may still reuse. Reports and crawl_counts stay, so History and crawl pace are unaffected; drill-downs read only the latest crawl.
  • Reports. compactReport keeps report_json under 1.5 MB (UTF-8 bytes), under D1's row limit, by dropping sampled pages, then evidence beyond the top findings, then route lists.
  • Finding keys before pruning. saveFindingKeys runs before pruning so History can still tell which pages vanished.
  • Server logs. pruneCrawlLog, called from apps/web/src/connector-sources.ts:290, drops crawl_log_paths rows not seen for 120 days and crawl_log_daily rows older than 486 days.
  • Replaced, not appended. search_metrics, page_search_metrics and every site_snapshots list are replaced on each sync.

WITHOUT ROWID tables

Small, write-heavy tables keyed by a composite primary key are declared WITHOUT ROWID: metric_points, page_links, url_index_status, page_metrics_daily, ai_page_daily, page_sessions (all from 0019), crawl_counts (0020), crawl_log_daily (0022), search_console_urls (0023), and site_access, site_access_invites, workspace_usage and workspace_github_installations (0024). The row is stored in the primary-key B-tree itself, so each upsert writes one row instead of a row plus an index entry. Use it for a new table when the key is the natural lookup and rows are small; keep the default for tables with large JSON payloads.

Applying migrations

Locally. npm run dev runs apps/web/scripts/predev.mjs first. It builds the shared packages, reads the local D1 file under apps/web/.cloudflare/state to see which migrations are unapplied, and if any are, runs npm run db:migrate:local (stopped after two minutes, since the cf CLI sometimes never exits). If migrations are still pending afterwards it prints which ones. You can run it yourself:

npm run db:migrate:local    # root script, delegates to apps/web
# = cf d1 migrations apply <db id> --local --persist-to ./.cloudflare/state --dir ../../packages/db/migrations

Remotely. npm run db:migrate:remote applies the same directory to the production database. The owner runs it on deploy; merging a migration does not apply it. See Operating it.

Code can reach production before its migration. Where that would break something important, the code tolerates the missing table: saveAnalysisReport wraps the ledger point, the finding keys and pruning in try/catch so the report is still saved. Do the same when a new write is secondary to the request.

The SQLite test shim

openSqliteD1 (packages/db/src/sqlite.ts:12, exported as @organic-growth/db/sqlite) opens Node's built-in node:sqlite (in memory by default), applies every .sql file in packages/db/migrations in order, and returns a D1Like. Every test that touches the database uses it: the packages/db/src/*.test.ts files and agents tests such as pipeline.test.ts and assistant.test.ts. scripts/audit-site.mjs (npm run audit) uses it too. It is not for use inside Workers.

The migrations seed rows: 0024 inserts the ws_initial workspace and its workspace_limits row. A fresh database is therefore not empty, and a test that checks "nothing is left" compares row counts with a fresh database, as the demo test does (packages/agents/src/demo.test.ts:94).

Because it runs the real migrations, a new migration is tested the moment you run npm test -w @organic-growth/db, and a migration that fails on SQLite fails there first. It needs Node 22 (node:sqlite).

The table rebuild rule

SQLite can't add a foreign key or change a column constraint on an existing table, so a migration that needs to rebuilds it: create x_new with the new shape, copy the rows that still have an owner, drop x, rename x_new to x. 0019 does this for fifteen tables.

A new nullable column that only references another table does not need a rebuild: ALTER TABLE … ADD COLUMN … REFERENCES works when the column's default is null. 0024 adds sites.workspace_id this way, because rebuilding sites would have to drop it, and that drop would cascade into every site-owned table.

Dropping a table deletes its rows, and with foreign keys enforced that delete cascades into every table that already references it. Rebuild a parent (say analyses) while new children point at it and the drop empties them. 0019 sets pages and changes aside first (pages_kept, changes_kept), drops the old children, then drops and replaces analyses, then creates the new children and copies the kept rows back. Rebuilding sites or generated_pages the same way without that order would wipe most of the database. See the "Table rebuild" entry in CONTEXT.md.

Checklist for a new migration:

  1. Add the next numbered file to packages/db/migrations/; never edit an applied one.
  2. Give new site-owned tables site_id TEXT NOT NULL REFERENCES sites(id) ON DELETE CASCADE, and new workspace-owned tables workspace_id TEXT NOT NULL REFERENCES "organization" ("id") ON DELETE CASCADE.
  3. If you rebuild a table, set its children aside before dropping it, as above.
  4. Put the SQL that reads and writes it in packages/db/src, and test it with openSqliteD1.
  5. Keep requests to a fixed number of queries (batch with json_each, not one query per item): the Workers Free plan allows 50 D1 queries per request (CONTEXT.md, "Query budget"; Gotchas).
