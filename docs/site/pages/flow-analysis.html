Site analysis, end to end

What happens between pressing "Run analysis" and a finished report: the API route, every step of the Cloudflare Workflow in order, what each step reads and writes, and how progress, cancellation and crawl cost are handled. Read this before changing apps/web/src/analysis-workflow.ts or the crawl queue in packages/db/src/index.ts.

Starting a run: the POST route

POST /api/sites/[siteId]/analyses lives in apps/web/app/api/sites/[siteId]/analyses/route.ts:31. In order, it:

  1. Checks the caller with requireSite(request, siteId, "write"): 401 without a session, 404 when the site doesn't exist or isn't in the caller's workspace, 403 for a Client.
  2. Reads the JSON body. full is true only when the body has full: true; otherwise the run reuses crawl results that still stand (see step 2, enqueue-full-crawl).
  3. Looks at the latest analysis for the site (getLatestAnalysisForSite). If it is queued or running and analysisStalled(latest) is false, it answers 409 "An analysis is already running for this site."
  4. Charges one analysis to the workspace (charge, metric analysesPerDay, line 42); past the day's limit it answers 429. Nothing is charged before this point, so a 409 costs nothing.
  5. If the latest run was queued or running but stalled, it terminates that Workflow instance (errors ignored) and marks the old run failed with "It stopped making progress, so a new run replaced it." before starting the new one, so the old run cannot come back and write alongside it.
  6. Creates an id with createId("analysis").
  7. Demo branch. If siteId === DEMO_SITE_ID, it calls startDemoRun and returns 202 with status running. No Workflow is created: the demo site is served from memory and its run is simulated as the progress view polls (the progress route calls advanceDemoRun).
  8. Otherwise it inserts the analyses row with createAnalysis (status queued), then calls env.ANALYSIS_WORKFLOW.create({ id: analysisId, params: { analysisId, siteId, full } }). The Workflow instance id is the analysis id, which is how the cancel route and the stalled-run handling find it again.
  9. If create throws, the row is marked failed with the error, the analysis is given back (refund), and the route answers 503. On success it answers 202 with status queued.

analysisStalled (packages/db/src/index.ts:212) is true when a queued or running analysis has had no progress update for more than 45 minutes (STALL_MS), measured from progress.updatedAt, or from created_at if it never reported progress. A restarted local dev server ends Workflow runs without telling the database, which is what this catches.

The Workflow, step by step

Each step.do(name, ...) is a durable step: its return value is stored, and if the Workflow resumes, finished steps are not run again. That shapes two rules visible throughout the file. Step outputs stay small (only plain fields cross a step boundary, and the large report is written to D1 inside the step rather than returned). And work that can fail on its own (one crawl batch, one competitor) gets its own step, so a retry repeats only that piece.

The whole run body sits in one try. Any error that escapes marks the analysis failed with the error message and completed_at, then rethrows (apps/web/src/analysis-workflow.ts:207).

1. load-site

  • Writes: analyses.status = 'running' (updateAnalysisStatus), then progress stage sitemap, "Reading the sitemap".
  • Reads: the sites row (getSite). A missing site throws NonRetryableError("The site no longer exists.").
  • Returns: only plain connection fields: name, baseUrl, githubOwner, githubRepo, githubInstallationId, defaultBranch, gscProperty.
  • Retries: Workflow defaults (no retry config is passed).

2. enqueue-full-crawl

Calls queueFullCrawl(db, { analysisId, siteId, baseUrl, maxUrls: MAX_FULL_CRAWL_URLS, full }) from packages/agents/src/pipeline.ts:85, then sets progress stage crawl, "Crawling N sitemap URLs as Googlebot". queueFullCrawl:

  1. Reads every sitemap URL and its lastmod with auditSitemap, and robots.txt as it applies to Googlebot with fetchRobots (a failed fetch counts as no robots.txt).
  2. Unless full, lists the runs it may reuse from with listReusableAnalyses: the last completed analysis, plus up to three newer runs that were cancelled or failed part-way. For each, listCrawlStates reads the per-URL state in pages of 5,000 rows. For each URL the newest fetch wins.
  3. For each URL, up to maxUrls: a URL robots.txt blocks for Googlebot is queued as blocked and never fetched. Otherwise, if shouldReuse says the earlier result still stands, it is copied; else it is queued for fetching.
  4. Copies reusable results with reuseCrawlResults (an INSERT ... SELECT into pages that keeps the original crawled_at and sets reused_from), then queues the rest with enqueueAnalysisCrawlUrls (rows in pages with crawl_state pending or blocked). Both finish with recountCrawl, which rebuilds the crawl_counts rows from scratch.

shouldReuse (packages/agents/src/pipeline.ts:68) only carries over successful fetches (crawl_state = 'complete'). With a sitemap lastmod, a page changed on or after the day it was crawled is fetched again, and results older than 30 days are refreshed anyway. Without a lastmod, results older than 7 days are refreshed.

The step returns { declared, queued, reused, reusedFrom? }. queued counts URLs to fetch, excluding blocked ones; it drives the batch loop. declared and reused end up in the saved report.

3. crawl-batch-0, crawl-batch-1, ...

CRAWL_BATCH_SIZE
100 URLs per step
CRAWL_CONCURRENCY
6 fetches in flight within a batch
MAX_FULL_CRAWL_URLS
25,000 sitemap URLs per analysis (the comment puts that at about 250 Workflow steps)
Retries
limit: 2, delay: "10 seconds", backoff: "exponential"

Constants are at apps/web/src/analysis-workflow.ts:51. The loop runs while batch * 100 < queued + 100, one iteration more than the queue needs, and stops early when a batch returns 0. Each step:

  1. listPendingCrawlUrls(db, analysisId, 100): the next 100 rows of this analysis with crawl_state = 'pending'. If there are none, the step returns 0 and the loop ends.
  2. crawlGooglebotBatch(urls, undefined, 6) (packages/crawler/src/index.ts:380): fetches each URL as Googlebot with six workers. A fetch that throws becomes an outcome with an error instead of failing the batch.
  3. saveCrawlBatch (packages/db/src/index.ts:545): each fetched page becomes crawl_state = 'complete' with its status, title, empty-shell flag and a result_json of the page's signals; each error becomes crawl_state = 'failed' with the error in result_json. It updates crawl_counts by delta, sets analyses.crawl_recent, and replaces each fetched page's outgoing links in page_links. See Crawl cost.
  4. Progress: "Crawled X of N sitemap URLs as Googlebot", where X is min((batch + 1) * 100, queued). That message is an estimate; the exact numbers come from crawl_counts.

Because the step reads its URLs from the database instead of from a list fixed earlier, a retry picks up whatever is still pending. Every update in saveCrawlBatch is guarded by crawl_state = 'pending', so a retried save cannot change a row or a counter twice. Failed URLs stay failed; they are not fetched again in the same run.

4. list-competitors and research-<domain>

  • list-competitors sets progress stage competitors and returns the site's competitor domains from site_competitor_domains (listSiteCompetitorDomains), capped at MAX_COMPETITORS (5, packages/agents/src/pipeline.ts:167).
  • research-<domain>, one step per competitor, with retries: { limit: 1, delay: "10 seconds" }. It reports progress with { competitor, done, of } in detail, then calls researchSite(domain, undefined, { maxFiles: 15, maxUrls: 50_000 }): the competitor's sitemaps and a few sample pages, fetched as EumonBot. The result's sitemap families are cut to the 40 largest before returning, to keep the step output small.

One slow or failing competitor retries on its own and does not repeat the others. Nothing is written to D1 here; the research is passed in memory to the last step.

5. inventory

loadInventories(db, siteId, { analysisId }) (packages/agents/src/inventory-data.ts:12) reads up to three of the site's datasets with records (largest first) and computes each one's inventory: fill per field, duplicate records, and thin record pages in the crawl. Any error returns []. It is its own step so its queries have their own budget and a failure costs only the inventory findings. Read-only.

6. analyze-repository-and-site

The last step, with retries: { limit: 2, delay: "5 seconds", backoff: "exponential" }. It sets progress stage analysis, "Checking rendering, indexing, and search data", then gathers inputs:

  • Repository snapshot. Only when the site has a GitHub installation, owner and repo: createInstallationToken (with GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY), createGitHubApiClient, then buildRepoSnapshotFromGitHub on defaultBranch (default main), from @organic-growth/repo-analyzer.
  • LLM. createLlm(env) picks DeepSeek, Anthropic, or Workers AI depending on what is configured (packages/ai/src/index.ts:50). If none is, it throws and the step carries on without one: content types are then matched by name and the plan text stays deterministic.
  • Search Console. Only when gscProperty is set: googleAccessToken (apps/web/src/gsc-auth.ts:40, reads the encrypted Google credential from oauth_credentials), fetchSearchConsoleMetrics, then replaceCurrentSearchMetrics, which replaces the site's rows in search_metrics. An error here fails the step (it is not caught).
  • Not-found probe. probeNotFound(baseUrl, analysisId) fetches one URL that cannot exist. Its title, if the site answers under 400, tells the coverage query which page titles are soft 404s.
  • Crawl results and site data, in parallel: getCrawlCoverage (aggregate counts and issue examples over every crawl row), listCrawlPageResults(db, analysisId, 50), datasetCoverage, listSiteMarkets, listRecordKeys, listSiteCompetitorDomains.
  • Keywords. loadKeywords (apps/web/src/keywords-data.ts): the keyword lists from the Performance sync. An enrichment only: on error it is undefined.
  • Connector signals. loadConnectorLists (search results pages, suggested competitors, backlinks and link gap from site_snapshots, and six months of crawl-log days), crawlLogCoverage, and searchConsoleReconciliation, then loadTrendSignals (daily series from metric_points); connectorSignals combines them with the inventory. If anything in that chain throws, it falls back to empty lists plus the inventory, so connectors never fail an analysis.

Then runFullAnalysis (packages/agents/src/pipeline.ts:169) runs with maxPages: 25. It analyses the repository snapshot; samples up to 25 sitemap URLs and fetches each as a browser and as Googlebot; renders one page per template (up to six) in a real browser through the renderPages callback; refetches a sample three times to catch intermittent failures; compares competitors (using the LLM to label content types when there is one); and produces the findings, opportunities and growth plan. How findings are produced and ranked is on Findings.

renderPages (apps/web/src/analysis-workflow.ts:215) uses Browser Rendering through @cloudflare/puppeteer and the BROWSER binding. It intercepts requests, letting through only safe public URLs and same-origin navigations; request interception never sees WebSockets, so it also blocks ws://* and wss://* through a CDP session (best effort: if the browser lacks CDP sessions the page renders anyway, apps/web/src/analysis-workflow.ts:223). It waits for networkidle2 (20 s timeout, then whatever has rendered), and keeps a page's HTML only if it ended on the same origin. A page that fails is skipped; the others are kept.

After runFullAnalysis:

  1. With an LLM, synthesizePlanNarrative rewrites the plan's headline text for a business owner; the evidence-derived priorities are not changed.
  2. If the repository gave a framework fingerprint, updateSiteFingerprint writes it to sites.fingerprint_json.
  3. Progress stage saving, "Saving findings and growth plan".
  4. saveAnalysisReport (packages/db/src/index.ts:358) with the report plus sitemapUrlsDeclared and, when results were reused, crawlReuse.
  5. The step returns plan.highestImpactOpportunity, a single string. The full report can exceed the Workflow step-output size limit, which is why it is saved inside the step and not returned.

What saveAnalysisReport writes

  • analyses: report_json (passed through compactReport, which keeps it under 1,500,000 bytes by dropping sampled pages, then evidence beyond the top 10 findings, then repository route lists, then all evidence), summary, status = 'completed', completed_at. The update only applies while the run is still queued or running, so a cancelled run is never turned into a completed one.
  • metric_points: the site-health points for Results (analysisHealthPoints: crawl coverage counts and AI crawler access).
  • site_snapshots: the run's finding key list (saveFindingKeys, kind finding_keys) for the History tab. It runs before pruning because it needs the previous crawl's rows to decide which findings vanished. See Findings: History.
  • pages: pruneCrawlResults deletes the crawl rows of older analyses, keeping the latest two completed runs (KEPT_CRAWLS) and anything newer than the latest completed run. Reports and crawl_counts stay.

The last three are each wrapped in their own try: a missing table (code deployed before its migration) costs only that extra, never the report.

Progress reporting

Inside the Workflow, every stage change goes through a local progress(stage, message, detail?) helper that calls updateAnalysisProgress (packages/db/src/index.ts:222). That function writes analyses.progress_json:

  • stage and message: the current stage (sitemap, crawl, competitors, analysis, saving) and its text;
  • detail: stage-specific facts, such as the competitor being read;
  • history: when each stage began, appended only when the stage changes, last 12 kept, so the dashboard can time stages;
  • updatedAt: the time of this update, which analysisStalled reads.

The crawl's own numbers do not come from progress_json. They come from two places kept up to date by saveCrawlBatch:

  • crawl_counts (migration packages/db/migrations/0020_crawl_counts.sql): one row per analysis and page type (route family) with counters total, pending, blocked, fetched, failed, reused, ok, http_errors, empty_shells, noindex, challenges, plus first_at and last_at of this run's own fetches. The progress view reads these few rows instead of counting a 25,000-row crawl every poll.
  • analyses.crawl_recent: the last eight URLs of the latest saved batch, newest first, for the "just fetched" list.

GET /api/analyses/[analysisId]/progress (apps/web/app/api/analyses/[analysisId]/progress/route.ts) returns the job's status, progress, error, summary, stalled: analysisStalled(job), and crawl: getCrawlProgress (packages/db/src/index.ts:1057) merged with estimateCrawl. getCrawlProgress sums the crawl_counts rows, lists up to 40 page types by size, and looks up the crawl_recent URLs in pages (this run's own fetches only). estimateCrawl gives pages per minute and seconds left, and leaves both out until a minute and 100 pages have passed.

Cancellation

POST /api/analyses/[analysisId]/cancel (apps/web/app/api/analyses/[analysisId]/cancel/route.ts) answers 404 for an unknown analysis and 409 if it is not queued or running. Otherwise it terminates the Workflow instance (errors ignored: a restarted dev server may already have ended it) and sets the row to cancelled with completed_at.

Terminating the instance is not relied on alone. updateAnalysisProgress updates with WHERE id = ? AND status IN ('queued', 'running') RETURNING id and returns false when no row matched. The Workflow's progress helper turns false into NonRetryableError("The analysis was cancelled."), so a run whose instance kept going stops at its next progress update without retrying. The catch then tries to mark it failed, but updateAnalysisStatus has the same open-status guard, so the row stays cancelled.

A crawl batch reports progress after it saves, so a run cancelled mid-batch still writes that batch's rows before it stops. Rows written by a cancelled run are useful: listReusableAnalyses lets the next run reuse them.

Crawl cost

D1 counts rows read against a daily budget. A crawl runs up to about 250 batches, so any query in the batch loop that touches every row of the analysis costs one row read per sitemap URL per batch. The test comment in packages/db/src/crawl.test.ts:343 records that both crawl queue queries once did exactly that, and on a 23,000-URL site one crawl used D1's daily row budget. Two details in packages/db/src/index.ts prevent it.

listPendingCrawlUrls has no ORDER BY

SELECT url FROM pages
WHERE analysis_id = ? AND crawl_state = 'pending'
LIMIT ?

pages has primary key (analysis_id, url) and an index idx_pages_analysis_crawl_state on (analysis_id, crawl_state). With ORDER BY url, SQLite walks the primary key in URL order and reads past every already-crawled row to find pending ones, so later batches read almost the whole analysis. Without it, SQLite reads the next pending rows straight off the crawl-state index. The order of the crawl does not matter, so the query leaves it out on purpose (packages/db/src/index.ts:530).

saveCrawlBatch updates counters by delta

Counting the crawl after every batch would read every row. Instead, saveCrawlBatch works in groups of 40 outcomes, each group one D1 batch of statements:

  1. countDelta(-1) over the group's URLs that are still pending: their current contribution comes off crawl_counts;
  2. the row updates, each guarded by crawl_state = 'pending';
  3. countDelta(+1) over the group's URLs whose crawled_at equals this save's timestamp: their new contribution goes on, and first_at/last_at widen.

A retried save finds no pending rows and no rows with its new timestamp, so nothing moves twice. countDelta (packages/db/src/index.ts:1034) is an INSERT ... SELECT ... GROUP BY route_family ... ON CONFLICT DO UPDATE that adds each counter's condition, signed, to the existing row.

The subtract statement's filter is written +crawl_state = 'pending' AND url IN (...). The unary + stops SQLite from using the crawl-state index for that term, so it looks the batch's rows up by primary key (analysis_id=? AND url=?) instead of scanning every pending row of the analysis. The second test in the crawl queue query plans suite asserts that plan, and the first asserts that listPendingCrawlUrls uses idx_pages_analysis_crawl_state (packages/db/src/crawl.test.ts:342).

Adding an ORDER BY to listPendingCrawlUrls, or dropping the + in front of crawl_state, passes every functional test and still turns each batch into a full-analysis scan. Change either query only with the query-plan tests running. See Gotchas.

recountCrawl, which deletes and rebuilds an analysis's counters with a full count, runs only after queueing and after reuse, never inside the batch loop.
