Web app

Reference for apps/web: the dashboard's views and the components behind them, the sign-in, invitation and admin pages, every API route with who may call it, the shared server helpers, the public routes, and how access is controlled. Use it to find where a screen or an endpoint lives, and what stops the wrong person reaching it.

The dashboard

The whole dashboard is one client component, apps/web/app/page.tsx, rendered at /. It loads the site list from GET /api/sites, keeps the selected site, view, tab and Ask thread in the query string (?site=…&view=…&tab=…&thread=…) so a refresh or shared link lands on the same place, and switches views in place without route changes. Who is signed in: /api/me

On load the dashboard calls GET /api/me (apps/web/app/page.tsx:121). The route (apps/web/app/api/me/route.ts:7) returns the user's ID and email, every workspace they belong to with their role in each, the active workspace (the one on the session), and platformAdmin. The dashboard uses it to:

  • Show the active workspace's name in the top bar, a workspace switcher when the user belongs to more than one (it calls authClient.organization.setActive and reloads), an "Admin" link for platform admins, and "Sign out" (apps/web/app/page.tsx:182).
  • Hide write views from Clients. For a Client the rail keeps only Dashboard, Landing pages and Page results; Home, Data and Setup are filtered out, and a link to a hidden view falls back to the Dashboard (apps/web/app/page.tsx:132).
  • Show NoWorkspace when the user belongs to no workspace, for example because their invitation expired before they accepted it. Its one button creates a workspace through Better Auth and makes it active (apps/web/app/page.tsx:46, used at line 147).

apps/web/app/components/auth-client.ts is the browser side of Better Auth: createAuthClient with the organizationClient and magicLinkClient plugins. The dashboard, the People panel, /sign-in and /invite/:id use it for sign-in, sign-out, switching workspace, listing members and accepting invitations. Everything else goes through api().

The People panel

MembersPanel (apps/web/app/components/MembersPanel.tsx:35) is the first card in Setup, titled "People". It loads the workspace with authClient.organization.getFullOrganization() and lists members with their role, and invitations that are still pending. Members see the list; only Owners get the invite form and the "Remove" button (canInvite is role === "owner", apps/web/app/components/SetupView.tsx:77). Clients never reach Setup.

  • The form takes an email and a role: Member (every site) or Client (read-only, on the sites ticked below the role). A Client invitation must name at least one site.
  • It posts to POST /api/workspace/invitations, which returns a link of the form /invite/<invitationId>. The panel shows the link to copy and send by hand, because invitation email is off until email sending is enabled (apps/web/src/auth.ts:31).

Sign-in, invitation and admin pages

Sign in: /sign-in

apps/web/app/sign-in/page.tsx is a server component that reads the flags and renders SignInForm (apps/web/app/sign-in/SignInForm.tsx). One page signs people in and signs them up: the account is created on first use.

  • Google is always offered (authClient.signIn.social, apps/web/app/sign-in/SignInForm.tsx:54). It is the only method on Workers Free.
  • Magic link appears only when EMAIL_ENABLED is "true". Email and password (with a "Create an account" toggle) appears only when PASSWORD_SIGNIN is also "true" (emailEnabled and passwordEnabled, apps/web/src/auth.ts:26).
  • Turnstile is loaded only when an email method is shown, and its token is sent as x-captcha-response. Better Auth's captcha plugin checks it on sign-up, email sign-in, magic link, password reset and verification email (apps/web/src/auth.ts:118). Tokens are single use, so the widget resets after every attempt.
  • next is where to go after signing in. safeNext (apps/web/src/next-path.ts:2) returns it only when it is a path on this site; anything starting // or /\, containing control characters or whitespace, or resolving to another origin becomes /.

The gate sends signed-out page requests here with next set to where they were going, and api() does the same in the browser when any call answers 401 (apps/web/app/components/api.ts:26).

Accept an invitation: /invite/:id

apps/web/app/invite/[id]/page.tsx is public, so a person who has never signed in can open their link. Signed out, it asks them to sign in with the invited address and links to /sign-in?next=/invite/<id>. Signed in, "Accept invitation" calls authClient.organization.acceptInvitation, makes that workspace active, and opens the dashboard. Accepting a Client invitation copies its sites into site_access (afterAcceptInvitation, apps/web/src/auth.ts:107).

A new user whose email has a pending, unexpired invitation gets no personal workspace at sign-up, so they land in the invited one (setUpNewUser, packages/db/src/workspaces.ts:32).

Platform admin: /admin

apps/web/app/admin/page.tsx lists every workspace with its site count, people and today's usage against each metered limit, and a form per workspace to change its limits. Numbers left empty mean unlimited; the three features are checkboxes. It reads GET /api/admin/workspaces and saves with PUT /api/admin/workspaces/:workspaceId/limits. The route merges what it is sent into the workspace's overrides and drops any value equal to the free default (mergeOverrides, apps/web/src/limits.ts:27), so a limit saved at its free value keeps following FREE_LIMITS. Anyone signed in can load the page, but the API answers 404 to anyone who is not a platform admin, and the page then shows "Not found." The dashboard's "Admin" link appears only for platform admins.

The client API helper

Every dashboard call goes through api() in apps/web/app/components/api.ts:10:

  • api<T>(path, init) calls fetch with cache: "no-store". Passing json in init serialises it and sets Content-Type: application/json.
  • On a 401 it sends the browser to /sign-in?next=<current path>, unless it is already on the sign-in page.
  • On any non-2xx response it throws ApiError, carrying the server's { error } message (or Request failed (status)) and the status.
  • errorMessage(error) turns anything caught into a display string.

The same file has the formatting helpers formatNumber, formatDay and percent. The one dashboard call that does not use api() is the Ask stream (POST /api/sites/:siteId/assistant), which reads server-sent events with a raw fetch in Ask.tsx. Account calls go through authClient (above).

How analysis progress is polled

apps/web/app/components/AnalysisProgress.tsx polls GET /api/analyses/:analysisId/progress outside React, in a module-level watches map, so polling continues when the user leaves the Dashboard.

  1. watch() starts a loop for one analysis and drops any older watch for the same site.
  2. Each tick fetches the progress route and notifies subscribers; components read it with useRun or useSiteRun (both useSyncExternalStore).
  3. The next tick is 2.5 seconds later, or 15 seconds when the run is reported stalled. A 404 ends the loop.
  4. When the status is completed, failed or cancelled, the loop stops, the tab title changes, and a browser notification fires if the user allowed them.
  5. While polling, the tab title shows the stage or crawl percentage, and the top bar shows a run chip on other views.

The progress route (apps/web/app/api/analyses/[analysisId]/progress/route.ts) returns the job's status, stored progress and stage history, whether it is stalled, and crawl counts with pace and time left. For the demo site it advances the simulated run on each poll. How the workflow writes that progress is on Analysis flow.

"Sync now" is polled separately: OverviewView.tsx checks the sync record every four seconds for up to fifteen minutes and asks GET /api/sites/:siteId/results/sync?id=… for the Workflow instance status. See Results sync flow.

API routes

Each path is a route.ts under apps/web/app/api/; :name is a [name] folder. The Who column is the guard each handler calls first (Access control explains the guards):

Public
The gate lets the request through without a session; the route checks its own credential (a token, a signed link, an Origin).
Signed in
Any session (requireViewer).
Read
Owner or Member of the site's workspace, or a Client granted that site (requireSite or requireOwned with "read").
Member+
Owner or Member of the site's workspace ("write"). A Client gets 403.
Owner
Owner only ("admin").
(workspace)
Checked against the session's active workspace instead of a site (requireWorkspace).
Platform admin
A verified email listed in BOOTSTRAP_OWNER_EMAIL (requirePlatformAdmin).

The Limit column names what the call is counted against (free limits); blank means it is not metered.

Routes keyed by an ID other than a site (/api/analyses/:analysisId, /api/fixes/:fixId, /api/datasets/:datasetId, /api/jobs/:jobId, /api/records/:recordId, /api/sources/:sourceId, /api/templates/:templateId, /api/pages/:pageId) are guarded through the site that owns the row. requireOwned (apps/web/src/guard.ts:41) looks up the row's site_id in its table (OWNER_TABLES, apps/web/src/access.ts:13), answers 404 if the row does not exist, and then applies the same check as a site route. Every one of those tables carries site_id directly, so there is one lookup per call.

Public routes

Landing pages: /p/:siteId/…

apps/web/app/p/[siteId]/[[...path]]/route.ts exports GET, HEAD and POST. It looks up the site (404 if unknown) and hands off to apps/web/src/public-pages.ts:

  • servePublicGet (apps/web/src/public-pages.ts:87) serves, under the site's mount path: a health check at /__eumon/health, the IndexNow key file, sitemap.xml, robots.txt (only when there is no mount path), the hub page, and each published page. Unpublished or retired pages return 410.
  • Responses carry X-Robots-Tag: noindex unless the request came through the customer's proxy (X-Eumon-Proxy: 1 or a matching X-Forwarded-Host).
  • HTML responses carry PAGE_HEADERS (apps/web/src/headers.ts:15), not the dashboard's headers, because the customer's site may frame them.
  • POST is accepted only on the beacon path /__eumon/e: servePublicBeacon records page views and CTA clicks from the rendered page's inline script, with first-touch session attribution through the eumon_sid cookie.

The full flow from dataset to served page is on Landing page flow.

Conversion events with CORS

apps/web/app/api/sites/[siteId]/events/route.ts receives events from the tracking snippet (from GET /api/sites/:siteId/integration).

  • OPTIONS and POST accept a request only when its Origin is the same site as the site's baseUrl or its landing-page publicOrigin (www and apex count as one). Otherwise 403.
  • The allowed origin is echoed in Access-Control-Allow-Origin with Vary: Origin; preflight allows POST, OPTIONS and Content-Type, cached for a day.
  • The body is capped at 4096 bytes, the event name must be one of a fixed list (page_view, cta_click, whatsapp_click, form_submit and others), and pageUrl must be on the allowed origin. A whatsapp_click with a reference code also records a lead click.
  • It answers 202 { accepted: true }.

Client share link: /r/:token

apps/web/app/r/[token]/page.tsx renders ClientReport, which loads GET /api/r/:token and shows the Results sections read-only, without site health, AI readiness checks or controls. The token is signed with SESSION_SECRET, carries purpose: "results", the site ID and the site's share version, and lasts five years (apps/web/src/share.ts). Revoking bumps the share version, which invalidates every earlier token. Share links need no account; a Client account is the signed-in alternative.

PWA files

apps/web/public/ holds manifest.json and the icons, referenced from apps/web/app/layout.tsx, so the dashboard can be installed as a standalone app. public/sw.js is still a retired service worker: nothing registers it, and its only job is to clear the old offline cache and unregister itself in browsers that installed an earlier version. The gate lists /sw.js as public (apps/web/src/gate.ts:14) so a browser without a session can still fetch it and clean up.

Access control

The app has its own accounts, built on Better Auth with its tables in D1 (migration 0024_accounts.sql). Every request passes two checks: the gate in the Worker, then a guard in the route. Cloudflare Access is not part of it.

The gate

apps/web/worker.ts:31 wraps vinext's handler. Before any page or route runs:

  1. /api/auth/* goes straight to Better Auth. Non-GET calls (sign-in, sign-up, magic link) are first rate limited by the AUTH_RATE_LIMIT binding, 10 a minute per cf-connecting-ip, and answer 429 past that. The endpoints that list a workspace's people (get-full-organization, list-members, list-invitations) answer 403 to a Client of any workspace the request could resolve to (apps/web/src/auth-paths.ts:2), because Better Auth only checks membership there.
  2. Everything else goes through gate(request, signedIn) (apps/web/src/gate.ts:21).

The gate's rules:

  • Public paths pass (PUBLIC, apps/web/src/gate.ts:7): /p/*; /api/sites/:siteId/events; /r/* and /api/r/*; /api/logs/*; /api/github/webhook; /api/auth/*; /sign-in and /invite/*; and the static files /manifest.json, /sw.js, /favicon.ico, /robots.txt, /icon-*.png and /assets/*.
  • A session is required for everything else. Signed out, /api/* answers 401 { error: "Sign in to continue." } and a page answers 303 to /sign-in?next=<path>.
  • Writes must come from Eumon's pages. A signed-in /api/* request with a method other than GET, HEAD or OPTIONS whose Origin header is not the app's own origin answers 403 (public paths are exempt; they never reach this check). The session cookie rides along on cross-site requests, so this is the CSRF check.

A route someone forgets to guard is therefore still not public. The gate only proves that someone is signed in; whether they may touch a given site is the guard's job.

Responses outside /p/* get APP_HEADERS (apps/web/src/headers.ts:7): X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, X-Frame-Options: DENY, and a CSP of frame-ancestors 'none'; base-uri 'self'; object-src 'none'. Neither header set restricts script-src: vinext writes inline scripts and the landing-page beacon is inline, so a script policy would need per-request nonces. The renderer's escaping is the XSS defence until then.

Roles

A workspace is a Better Auth organization; a person's role is their member.role in it. allows(role, need) (apps/web/src/access.ts:6) is the whole rule: Owners pass everything, Members pass read and write, Clients pass read only.

RoleSeesCan
OwnerEvery site in the workspaceEverything a Member can, plus delete sites (DELETE /api/sites/:siteId is admin), invite people and remove them.
MemberEvery site in the workspaceRead and change every site: add sites (within limits), run analyses, connect GitHub and Google, manage data and landing pages, publish, open pull requests, use Ask, export. Sees the People list but cannot invite.
ClientOnly the sites in site_access for themRead only: the Results dashboard, landing pages and their results, leads, history. No settings, connections, Ask, publishing, deletes, pull requests or exports, and not the workspace's People list.

Better Auth's own permissions match: client is defined with no organization, member or invitation permissions (apps/web/src/auth.ts:40).

Workspaces

  • New users. When Better Auth creates a user, setUpNewUser (packages/db/src/workspaces.ts:32) gives them a personal workspace as its Owner, unless an unexpired invitation is waiting for their email. Each new session opens in the user's first workspace (workspaceForNewSession, line 55).
  • One owned workspace per user. organizationLimit is (user) => ownsWorkspace(db, user.id) (apps/web/src/auth.ts:93), so creating a workspace through the API is refused once the user is Owner of one, and free limits can't be multiplied. ownsWorkspace (packages/db/src/workspaces.ts:86) looks only for an owner row: being a Member or Client of other workspaces doesn't stop someone creating their own. The personal workspace made at sign-up is written directly and is not affected.
  • Deletion is disabled. disableOrganizationDeletion: true (apps/web/src/auth.ts:95). sites.workspace_id also has no cascade, so the database refuses to delete a workspace that still has sites (packages/db/migrations/0024_accounts.sql:27).
  • Invitations and grants. A Client invitation stores its sites in site_access_invites; accepting copies them to site_access, after first removing any grants the user already had in that workspace. Removing a member deletes their grants (apps/web/src/auth.ts:107).
  • Sign-in methods. Google is always on, with sign-in tokens kept to sign-in scopes (includeGrantedScopes: false) so it does not pick up the Search Console grant. Magic link and email verification need EMAIL_ENABLED; email and password needs PASSWORD_SIGNIN as well (apps/web/src/auth.ts:26). Sessions last 30 days.

The tables are described on Data model: sites and ownership.

A route makes its own checks before it charges: a run already going (409), no model configured (503), bad input (400), a missing Ask thread (404). A refused request costs nothing. A model call that fails after the charge is not refunded. An Ask question or AI run that errors still uses one of the day's allowance.

Bootstrap owner and platform admins

BOOTSTRAP_OWNER_EMAIL is a comma-separated list. A listed user with a verified email joins the initial workspace ws_initial as Owner instead of getting a personal one, and every new session puts them back in it as Owner if the list grew after they signed up (packages/db/src/workspaces.ts:55). Migration 0024 creates ws_initial and moves every site that existed before accounts into it. The same people are platform admins: they get platformAdmin: true from /api/me and can use /admin.

Per-site log tokens

POST /api/logs/:siteId stays public because log shippers cannot sign in. It accepts the token from Authorization: Bearer … or ?token=, and gives the same 401 for an unknown site and a wrong token (apps/web/app/api/logs/[siteId]/route.ts:18).

  • While sites.log_token is null, the expected token is the one derived from SESSION_SECRET (logToken, apps/web/src/crawl-logs.ts:13), so log drains set up before accounts keep working.
  • "Rotate token" in Setup's log card (apps/web/app/components/ConnectorSetup.tsx:237) calls POST /api/sites/:siteId/connectors, which stores 32 random bytes as hex (apps/web/app/api/sites/[siteId]/connectors/route.ts:53). From then on only the stored token is accepted (tokenMatches, apps/web/src/crawl-logs.ts:21); paste it into the log shipper.

The log route refuses every delivery when SESSION_SECRET is unset, even for a site with a rotated token. Setup only shows the log address when SESSION_SECRET is at least 32 characters.

GitHub installation ownership

An installation_id in the install callback's query string proves nothing, because anyone can type one. /api/github/callback first checks the og_github_state cookie, then needs the code GitHub sends when the App has "Request user authorization (OAuth) during installation" turned on. checkInstallation (apps/web/src/github-install.ts:11) exchanges the code for a user token and accepts the installation only if:

  • it is in the user's /user/installations (first 100), and
  • it is on the user's own account, or on an organization where the user is an active admin.

An organization whose membership GitHub won't show (403 or 404) is refused as org_permission_missing; the App needs Organization permissions, Members: Read-only. Accepted installations are stored per workspace in workspace_github_installations, which replaces the old og_installation cookie (the callback expires it). Each refusal reason maps to a message in apps/web/app/page.tsx:111.

Google connection state

A signed OAuth state only proves Eumon made it. /api/sites/:siteId/gsc/connect signs { siteId, nonce, userId } into the state and sets the nonce in an HttpOnly cookie scoped to /api/google/callback for ten minutes. The callback (apps/web/app/api/google/callback/route.ts:12) refuses unless googleStateProblem (apps/web/src/google-state.ts:11) finds the state valid, the cookie nonce equal to the state's, and the signed-in user the one who started; then it requires Member+ on that site. So nobody can send someone a link that stores the victim's Google account on the sender's site. Every answer expires the nonce cookie.

What fix pull requests may change

Every fix passes validateEdit or validateFile (packages/fixes/src/validate.ts) before it is staged. They refuse a path outside ALLOWED_FILES (route page files, the root layout, components/eumon-json-ld.tsx, public/llms.txt, public/robots.txt), a path the repository analysis marks sensitive or that matches its sensitive patterns, an edit outside the metadata object or JSX spot Eumon chose, a pure deletion, a new import other than Eumon's component, any code shape Eumon never inserts (calls, functions, computed members), and a name not in scope. The model writes only words; see Code fixes.
