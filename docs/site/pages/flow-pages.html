The landing-page engine

How Eumon turns a business into many specific landing pages on the customer's own domain: scoping the datasets, collecting records, deduping, generating pages from templates, serving them through the customer's proxy, measuring visits and leads, and improving the pages afterwards.

Scope

POST /api/sites/:siteId/scope (apps/web/app/api/sites/[siteId]/scope/route.ts) breaks the business into the granular things people search for. It takes an optional goal (up to 600 characters) and needs a language model.

  1. gatherSiteEvidence (apps/web/src/page-engine.ts:26) collects the evidence: route groups summarised from the sitemap, the homepage, one example page from each of the top four route groups, shallow links from the homepage, the site's top Search Console queries (from search_metrics), and the detected framework. If the homepage can't be read the route answers 422.
  2. proposeScope (packages/scraper/src/scope.ts:93) asks the model for the business name, a summary, the conversion goal, and 2 to 4 datasets. Each dataset has typed fields (text, number, list, url, boolean), a key field, page ideas (one page per record, or grouped by one or two fields) and candidate sources.
  3. validateProposal enforces the invariants whatever the model returned: at most 4 datasets and 25 fields each, snake_case keys, a key field that exists, at least 2 fields, and only the key field required (a record missing other details still becomes a thinner page).
  4. The route deletes unused proposed datasets, saves the scope to site_scopes, and inserts each dataset with status proposed and its sources with status proposed. Default page budgets: 50 for page sources, 2,000 for own_site, 300 otherwise. If the site has no page_settings yet, the business name the model found becomes the site name.

Proposals stay proposals until the owner approves sources and collects data. POST /api/sites/:siteId/datasets creates a dataset by hand instead.

Datasets and sources

A source is one place records can be collected from. Its kind is one of own_site, listing, sitemap, page or supabase (apps/web/src/datasets.ts:4). expandSource (packages/scraper/src/discover.ts:26) turns a source into the detail-page URLs to read:

KindWhat is read
pageThe URL itself, then its pager (rel=next), up to maxPages and at most 50 pages. For a table or list of many records on one page.
sitemap, own_siteSitemap URLs filtered by urlPattern (for example /doctors/*). own_site always uses the site's own origin. A pattern is required.
listingLinks on a listing page that match urlPattern, following rel=next for up to 50 list pages. Without a pattern every same-site link is included, with a note.
supabaseA table or view in a Supabase project, read with a read-only key that is sealed at once and never returned (apps/web/src/supabase-source.ts).

The source routes:

  • POST /api/datasets/:datasetId/sources adds a source as approved. It checks the URL is public, validates the pattern, and clamps maxPages to 1–50 for page and 1–5,000 otherwise.
  • PATCH /api/sources/:sourceId approves, rejects, or edits the pattern and page budget. DELETE removes it (and a Supabase key).
  • POST /api/sources/:sourceId/preview (apps/web/app/api/sources/[sourceId]/preview/route.ts) is a dry run: how many URLs match, how many robots.txt blocks, the first 10, and what the extractor pulls from the first page (up to 20 records). It stores robotsAllowed and any error on the source.

Collection

POST /api/datasets/:datasetId/scrape creates a jobs row and a ScrapeWorkflow instance whose id is the job id, then answers 202. It refuses with 409 when a run for the dataset is queued or running and less than 6 hours old, or when no requested source is approved. GET /api/jobs/:jobId returns the job, queue counts and recent failures for the progress view.

ScrapeWorkflow (apps/web/src/scrape-workflow.ts) runs these steps:

  1. load: marks the job running and turns a proposed dataset active.
  2. Supabase pulls: each supabase source is read a page per step by runSupabasePull.
  3. expand-<sourceId>: expandSource for each other source, writing the URLs into scrape_queue (INSERT OR IGNORE on job, source and URL) and the source's robots status and error.
  4. queued: fails the job if no source produced pages and there were no tables.
  5. scrape-batch-N: 8 queued URLs per step, up to 900 steps. Each URL is fetched, its records extracted and upserted, and its queue row marked done, failed or skipped (blocked by robots.txt). Requests to the same host are spaced at least 1.5 seconds apart for third-party hosts, 300 ms for own-site sources, or the robots.txt Crawl-delay if longer, capped at 20 seconds.
  6. merge-duplicates: merges records that name the same thing (skipped when every source is a table). A failure here doesn't fail the run.
  7. finish: refreshes each source's record count and writes the summary message.

PoliteFetcher (packages/scraper/src/fetch.ts:10) fetches as EumonBot with robots.txt enforced per origin. It fetches each origin's robots.txt once per instance: a 5xx or network error means disallow everything, a 4xx means allow everything. A disallowed URL throws RobotsBlockedError.

extractRecordsFromHtml (packages/scraper/src/extract.ts:101) sends the page's JSON-LD, meta and cleaned text to the model with the dataset's fields and asks for records using only facts on the page. A page with under 80 characters of text and no JSON-LD is skipped without a model call. normalizeRecords coerces each field to its type, slugifies the key field into the record key, drops rows without a key, removes a record from its own list fields, and merges repeats of the same key on one page.

An LlmError (a truncated, refused, empty or malformed answer, or no model configured) fails only that page. Any other error, such as the model provider being unavailable, fails the step so Workflows retries it (up to 2 retries, exponential backoff from 15 seconds).

CSV import. POST /api/datasets/:datasetId/records/import takes a CSV body of up to 5 MB. parseCsv handles RFC 4180 quoting; mapCsvRows matches headers to fields by key or label, case-insensitively, then runs the same normalisation. Rows are saved with source_url = "csv-import", and a proposed dataset becomes active.

Every path writes records with upsertRecords (packages/db/src/page-engine.ts:222), which merges into an existing record with the same key: new single values win, gaps are filled, list values accumulate, and the first source URL is kept.

Dedupe and potential

Pages often name the same entity in different ways ("Riverside Clinic" and "Riverside Medical Clinic"). findDuplicateRecords (packages/scraper/src/resolve.ts:32) sorts the distinct names and sends them to the model in windows of 400 that overlap by 40. Every member it returns must be an existing name, and a name joins at most one cluster. mergeDuplicateRecords (apps/web/src/dedupe.ts:10) then merges each cluster's data into the canonical record. It runs at the end of a collection and on demand from POST /api/datasets/:datasetId/dedupe.

GET /api/datasets/:datasetId/potential returns estimatePagePotential (packages/pages/src/potential.ts:112) over up to 20,000 records: for each page idea, how many pages would pass the quality gate, how many are thin, and how many grouped pages would duplicate another. It also suggests groupings nobody proposed when the data supports at least 2 pages. It uses the same thresholds as generation, so the estimate matches what will be published.

Records are browsed with GET /api/datasets/:datasetId/records (search with q, up to 200 per page) and removed with DELETE /api/records/:recordId. GET /api/datasets/:datasetId/inventory reports field fill, duplicates, thin and missing pages.

Templates and generation

POST /api/datasets/:datasetId/templates designs a template for one page idea (by ideaIndex, by groupBy, or the entity idea by default) and generates its pages as drafts. It needs at least one record.

The AI writes copy patterns once per template, never per page. proposeTemplate (packages/pages/src/templates.ts:147) shows the model the 5 most complete records and field coverage, and asks for a path pattern, title, description, H1, intro, item fields, sort, minimum records and FAQ, all written with placeholders such as {field_key}, {count}, {min:field}, {site} and {year}. Unknown placeholders and fields fall back to the data-only defaultTemplate, which is also used when no model is configured, when useAi is false, or when the model call fails.

regenerateTemplate (apps/web/src/page-engine.ts:73) loads up to 20,000 records (more is an error), links to entity pages of other templates, and calls generatePages (packages/pages/src/generate.ts:58). Generation is deterministic: the same data and template give the same paths and copy.

  • Grouping: one page per record for an entity template, or one per combination of the groupBy values. A page lists at most 100 records.
  • Paths: built from the path pattern under the mount path. Paths of pages that are or were live are kept as-is; a new path that collides gets -2, -3 and so on.
  • Quality gate (assessQuality, packages/pages/src/generate.ts:273): a page needs a title. An entity page must fill at least 40% of the fields at least 20% of records have, and have at least 250 characters of intro, item and FAQ text. A grouped page needs the template's minRecords. A failing page gets status thin and a quality score of 0, with its issues listed. A title over 65 characters adds a warning but doesn't fail.
  • Duplicates: a grouped page listing exactly the same records as an earlier one becomes duplicate.
  • Facts (buildFacts): the record count and, for each number field, its min and max.
  • Related links (attachRelatedLinks): up to 6 sibling pages that share the most group values (or, for entity pages, short text and list values). Values shared by more than 20 pages and more than half of all pages are ignored.

syncTemplatePages (packages/db/src/page-engine.ts:515) writes the result to generated_pages. A page that was published or unpublished keeps that status and its path. A page that no longer exists in the output is marked retired if it was ever live (so it answers 410), and deleted otherwise. POST /api/templates/:templateId/generate runs regeneration again after the data changes.

Publishing and serving

POST /api/templates/:templateId/publish publishes every draft or unpublished page with a quality score above 0 and sets the template active; { publish: false } unpublishes. Thin and duplicate pages never go live, and PATCH /api/pages/:pageId refuses to publish them with 409.

The customer's site proxies a path (by default /guides, the mountPath in page_settings) to /p/:siteId/… on Eumon. apps/web/app/p/[siteId]/[[...path]]/route.ts resolves the site and hands off to servePublicGet (apps/web/src/public-pages.ts:86):

Path under the mountResponse
/__eumon/healthJSON { ok, siteId, proxied }, used by the setup check
/<32 hex>.txtThe site's IndexNow key file, when SESSION_SECRET is at least 32 characters
/sitemap.xmlrenderSitemap: the hub plus every published page, with lastmod
/robots.txt (empty mount path only)Allow all, pointing at the sitemap
The mount path itselfThe hub page: published pages grouped by template
Anything elseThe page by path. unpublished and retired answer 410; other non-published pages 404 unless ?preview=1.

A request counts as proxied when it carries X-Eumon-Proxy: 1, or an X-Forwarded-Host equal to the public origin's host. Only a published page served through the proxy, without ?preview=1, is indexable. Everything else gets X-Robots-Tag: noindex and a noindex, nofollow robots meta, so the copy on Eumon's own host never competes with the customer's URL.

renderLandingPage (packages/pages/src/render.ts:152) returns complete HTML with no JavaScript needed for content: a canonical link to the public URL, Open Graph tags, and JSON-LD (structuredData, line 60) with a BreadcrumbList, then a WebPage about the entity for single-record pages or an ItemList of up to 50 items for grouped pages, and an FAQPage when the page has FAQs. Before rendering, related links and item links to pages that are not live are dropped. Indexable pages are cached for 300 seconds; others are no-store. A published page fetched by Googlebot increments googlebot_hits; a fetch by a known AI agent is recorded in ai_page_daily.

GET /api/sites/:siteId/integration (apps/web/app/api/sites/[siteId]/integration/route.ts) returns the proxy snippets, a guess at the hosting provider and CMS from the homepage's headers, and the tracking snippet. The snippets are:

  • Cloudflare Worker: forwards the request and sets X-Eumon-Proxy: 1 and X-Forwarded-Host.
  • Vercel: rewrites in vercel.json.
  • Next.js: beforeFiles rewrites in next.config.js.
  • Netlify: a 200 redirect in netlify.toml with X-Eumon-Proxy = "1".
  • nginx: a location block with proxy_pass, X-Forwarded-Host and X-Eumon-Proxy.
  • Apache: ProxyPass with RequestHeader set X-Eumon-Proxy "1".

The Vercel and Next.js snippets set no header themselves. If a proxy sends neither header, pages are served with noindex. The setup check catches this as "Proxy identifies itself".

POST /api/sites/:siteId/integration verifies the setup from outside as Googlebot: the health path answers through the proxy with the right site id and proxied: true, a published page returns 200 with Eumon's generator meta and isn't an empty shell, it has no noindex, and its canonical equals its URL. When every check passes it stores verifiedAt in page_settings, which the IndexNow source of the daily sync waits for. Changing the public origin or mount path clears it.

Measurement

On landing pages. trackingScript (packages/pages/src/render.ts:134) sets a first-party eumon_sid cookie for 30 days and posts beacons to <mount>/__eumon/e on the same origin. servePublicBeacon ignores bots and unpublished pages, then:

  • a view increments views in page_metrics_daily (and the CTA variant's impressions), records the first landing in page_sessions with its source (search engine or AI assistant, from the referrer host and utm_source), and an AI referral in ai_page_daily once per session;
  • a cta click increments cta_clicks (and the variant's clicks) and inserts a conversion_events row typed from the CTA's URL: whatsapp_click, phone_click, email_click or cta_click.

On the main site. The tracking snippet from the integration route posts to POST /api/sites/:siteId/events (apps/web/app/api/sites/[siteId]/events/route.ts). It reuses the eumon_sid cookie when the landing pages share the domain, so a conversion is credited to the page the visitor first landed on. It tracks WhatsApp, phone and email links and form submissions, never form contents, and exposes window.eumonTrack. The endpoint:

  • answers CORS preflight and posts only for an Origin on the same site as the site's base URL or its public origin (www and apex count as the same), echoing that exact origin, otherwise 403;
  • rejects bodies over 4,096 bytes (413), unknown event names, and a pageUrl from another origin;
  • stores the event in conversion_events and answers 202.

WhatsApp reference codes. Both scripts share WHATSAPP_REF_JS (packages/core/src/whatsapp.ts). On a click of a wa.me or api.whatsapp.com link they append a 5-character code to the pre-filled message, for example "… (ref K7M2Q)", using letters and digits that can't be misread. The click carries the code, and the server records a leads row with status clicked. Staff match the code in the chat, then move the lead through chat, qualified, won or lost with PATCH /api/sites/:siteId/leads/:leadId, which updates the Results ledger at once.

The page-search step of the daily sync adds Search Console data for the pages: page × query rows in page_search_metrics, and daily clicks and impressions in page_metrics_daily.

Optimisation

CTA variants. POST /api/sites/:siteId/cta-variants adds a variant; the first one also enrols the current default CTA as the control. PATCH …/cta-variants/:variantId turns a variant on or off. On each page render, chooseArm (packages/pages/src/bandit.ts:12) picks among active variants by Thompson sampling: each variant's click-through rate has a Beta posterior, and the variant with the highest draw is shown. The prior is centred on the pooled rate across variants and worth 10 views, so a new variant starts "about average, very uncertain". With no active variants the page uses the CTA from page_settings.

Performance report. GET /api/sites/:siteId/performance?days=28 runs buildPerformanceReport (packages/pages/src/insights.ts) over page performance, page queries and variants. It returns totals, per-template stats, top pages and a ranked list of suggestions: rewrite_snippet (click-through rate under half of what the position usually gets), target_queries, not_crawled, no_visibility, weak_cta, expand_template, start_cta_test and cta_winner. Each suggestion carries its evidence and a rough impact used for ranking.

Title suggestions. POST /api/pages/:pageId/snippets calls suggestSnippets (packages/pages/src/snippets.ts), which asks the model for three different title and description options grounded in the page's facts and its real queries from page_search_metrics, in the page's language.

Revisions. PATCH /api/pages/:pageId edits a title (10–90 characters), description (30–200) or status. updatePageFields (packages/db/src/page-engine.ts:670) stores edited copy as an override that survives regeneration and writes one page_revisions row per changed field with before, after, reason and author. The performance route returns the latest 30 revisions with equal windows of views, CTA clicks and search clicks before and after each change (up to 14 days a side). { resetOverrides: true } drops the overrides and regenerates the template.
