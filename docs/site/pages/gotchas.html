Limits and gotchas

The platform limits production runs under, the incident that showed what they mean in practice, and the traps in queries, local development, the monorepo and git that have cost this project time. Read it before changing a Workflow, a crawl query or the dev setup.

Workers Free plan limits

Production runs on the Workers Free plan with D1 Free, by choice. The figures below are Cloudflare's published Free-plan limits; localhost (Miniflare) enforces none of them, so code that works locally can still fail in production.

LimitFree planWhat happens when it is hit
Subrequests to the internet (fetch to other hosts)50 per invocationThe next fetch throws "Too many subrequests".
Calls to Cloudflare services (D1, Workflows, AI, Browser and so on)1,000 per invocationThe next call throws "Too many API requests by single Worker invocation".
CPU time10 ms per invocationThe invocation is ended with an exceeded-CPU outcome.
D1 rows read5,000,000 per dayEvery query fails until 00:00 UTC.
D1 rows written100,000 per dayEvery write fails until 00:00 UTC.

Rows read counts rows SQLite scans, not rows returned. A query that walks an index past 20,000 rows to return 100 costs 20,000 reads.

What in Eumon is shaped by them

  • Inspection steps of 40. The Results sync calls Google's URL Inspection API 40 URLs per Workflow step (INSPECTION_STEP, apps/web/src/url-inspection.ts:8), so each step stays under 50 subrequests (apps/web/src/search-sync-workflow.ts). Whether the 50-subrequest limit applies per step or per Workflow instance has not been confirmed in production; watch Sync history for "Too many subrequests".
  • Crawl batches. The analysis crawls 100 sitemap URLs per step, 6 at a time (CRAWL_BATCH_SIZE and CRAWL_CONCURRENCY, apps/web/src/analysis-workflow.ts:52), and at most 25,000 URLs per analysis. 100 fetches is above the 50-subrequest cap: shrinking the batch is open work (see the incident below). Crawl results are saved 40 rows per D1 batch (packages/db/src/index.ts:611).
  • A cron trigger, not Workflow schedules. Workflow schedules need the paid plan, so the daily sync is a Worker Cron Trigger at 04:15 UTC that starts one search-sync instance per site (apps/web/cloudflare.config.ts:10, apps/web/worker.ts:14). Each site gets its own instance so each has its own step budget.
  • Work split into steps. Competitor research and the data inventory each run in their own Workflow step, so a slow or failing part retries alone and has its own query budget (the analysis flow).

Case study: the 2026-10-10 D1 outage

The first real production analysis of a large site ran against a sitemap of 22,913 URLs. It took production down for the rest of the UTC day and showed three limits at once.

What happened

  1. The crawl queued every sitemap URL and ran 108 crawl-batch-<n> steps of 100 URLs. They finished in about 15 seconds in total, because almost every fetch failed fast: D1 recorded 14,730 "mark failed" updates and no successful page saves.
  2. Batch 108 died on "Too many API requests by single Worker invocation", the 1,000-calls-to-Cloudflare-services cap. The Workflow instance errored.
  3. Meanwhile D1 hit the 5,000,000 rows-read daily limit. From then on every route that queries D1 returned 500 until 00:00 UTC. The analysis record stayed running, because the Workflow's attempt to mark it failed was itself a D1 write, and Cancel could not run because it reads D1 first (see the runbook).

Why D1 ran out

Two crawl-queue queries read every row of the analysis on every batch, so the cost of a batch grew with the size of the site instead of the size of the batch:

  • listPendingCrawlUrls had ORDER BY url. To return rows in URL order SQLite walked the primary key (analysis_id, url) and stepped past every already-crawled row to find pending ones.
  • The counter subtraction in saveCrawlBatch (crawl_state = 'pending' AND url IN (…)) made SQLite choose the idx_pages_analysis_crawl_state index and scan every pending row, instead of seeking the 40 URLs by primary key.

On a 23,000-URL site that was roughly 100,000 rows read per batch. How a crawl's D1 cost adds up is covered in the analysis flow.

The fix (PR #19)

listPendingCrawlUrls lost its ORDER BY and now reads the next pending rows straight off the crawl-state index (packages/db/src/index.ts:527). The subtraction uses +crawl_state, which keeps SQLite on the primary key (packages/db/src/index.ts:616). Measured on a scratch copy of that size, in SQLite VM steps:

QueryBeforeAfter
Next pending URLs55,809608
Counter subtraction120,6381,081

Still open

  • Why the fetches failed. The error text of the failed pages has not been read yet. That site is behind Cloudflare, so its bot protection may be refusing Googlebot-agent fetches from Workers; or the 50-subrequest cap is cutting off a 100-URL batch. Re-run the analysis and read the error on the failed rows (crawl_state = 'failed', message in result_json at $.error, packages/db/src/index.ts:550) before changing anything.
  • Calls per invocation. A Workflow invocation has to stay under 1,000 calls to Cloudflare services. Each crawl step does D1 reads, the save batches and a progress write that doubles as the cancel check; that total has to be counted against the cap, and batch size brought under 50 fetches.

A D1 quota outage is not a bug in the app, but it takes the whole app down: every page that queries returns 500 until midnight UTC, and nothing can be cancelled from the dashboard. Before running an analysis on a large site, check npx wrangler d1 info eumon-prod and the per-query reads in d1 insights (commands).

Query-plan traps

D1 is SQLite, and SQLite chooses an index without table statistics unless ANALYZE has run. With an equality on analysis_id in both the primary key and a secondary index, it often picks the one that reads more rows. The query is correct either way, so nothing fails; the rows-read bill is the only symptom.

  • Check the plan. Run EXPLAIN QUERY PLAN <query> against a local copy. SEARCH pages USING PRIMARY KEY (analysis_id=? AND url=?) is a seek; USING INDEX idx_… (analysis_id=? AND crawl_state=?) followed by row checks is a scan of every row the index matches. USE TEMP B-TREE FOR ORDER BY means a sort over every matched row.
  • The +column trick. Writing +crawl_state = 'pending' makes the column an expression, so SQLite cannot use an index on it and falls back to the other candidate. The result is unchanged.
  • ORDER BY on a large set. Leave it out when the order does not matter; it can force a walk of the whole key range.
  • Pin the plan in a test. packages/db/src/crawl.test.ts:342 ("crawl queue query plans") runs EXPLAIN QUERY PLAN on both crawl-queue queries and asserts the index each uses. Add a case there when you change a query that runs once per batch or per page.

Local timing hides this. A scan of 20,000 rows takes milliseconds in Miniflare and costs 20,000 reads in production, per call. Measure rows or VM steps, not time.

Local dev traps

One dev server per directory
vinext takes a lockfile when its dev server starts and refuses a second one in the same project root. Setting VINEXT_NO_DEV_LOCK=1 skips the lock (vinext/dist/cli-dev-config.js in apps/web/node_modules). For an isolated second server, use a separate Vite config with its own persistState path and cacheDir so it does not share the first server's D1 state or dependency cache. The dev server runs on port 5174 with --strictPort, so a taken port is an error, not a new port (apps/web/package.json).
Workers AI only works remotely
remoteBindings: false in apps/web/vite.config.ts:9 keeps every binding local, and the AI binding has no local simulation ("Binding AI needs to be run remotely"). Set DEEPSEEK_API_KEY or ANTHROPIC_API_KEY in .dev.vars to use the AI steps locally. Browser Rendering does work locally.
Undeclared .dev.vars entries are ignored
Only names declared in apps/web/cloudflare.config.ts reach the Worker; anything else in .dev.vars is dropped without a warning (apps/web/cloudflare.config.ts:59). Declare a new secret there before reading it. Restart the dev server after changing either file.
Local D1 runs one query at a time
In Miniflare a slow query blocks every other request, and the running query cannot be cancelled: only a dev-server restart recovers. Time a suspect query first, read-only, against the SQLite file under apps/web/.cloudflare/state with EXPLAIN QUERY PLAN, before sending it through the server.
The dev server blocks foreign origins
vinext's dev-origin check rejects requests whose Origin is not localhost, a .localhost subdomain, the request's own host, or listed in allowedDevOrigins (vinext/dist/server/dev-origin-check.js). So CORS endpoints such as /api/sites/*/events cannot be tested with a foreign Origin against the dev server. Requests with no Origin (plain curl) pass.
zsh echo rewrites JSON
zsh's echo turns \n inside a JSON string into a real newline, which breaks the JSON. Write responses to a file, or use printf '%s', before piping them to a parser.
"Network connection lost." on Google Analytics calls
A DNS blocker on the dev machine (a Pi-hole, for example) that answers 0.0.0.0 for analyticsadmin.googleapis.com or analyticsdata.googleapis.com shows up inside workerd as "Network connection lost.". Run getent ahosts analyticsdata.googleapis.com before debugging the code.

Monorepo traps

  • Packages import each other's built dist/. Every package's main and types point at ./dist (for example packages/core/package.json:6), and the web app imports the packages the same way. An edit to packages/*/src is invisible to the web app and to other packages until npm run build:packages runs. npm run dev rebuilds them first (apps/web/scripts/predev.mjs), but a running dev server does not; rebuild and reload after changing a package.
  • Tests run against compiled code. Each package's test script compiles with tsconfig.test.json into dist-test/ and runs node --test on that. A test in one package exercises the other packages' dist/, not their source. The root npm test runs build:packages first; running one workspace's tests does not.
  • Build order matters. build:packages in the root package.json builds core, ai, db, repo-analyzer, crawler, scraper, pages, agents, sdk in that order. A new package or a new dependency between packages needs a place in that list.

Git and worktree traps

Never run two shell commands in parallel that each cd into a different worktree under .worktrees/. When the shell's working directory is shared, one command's cd can land the other's edits in the wrong worktree; this has happened once. Run them one after the other, or use absolute paths with no cd.

A "keep both sides" conflict resolution, when both branches added a block at the same place, drops the closing lines the two blocks shared (a });, for example) and can duplicate a shared import. Run npm run build after resolving a conflict that way, before committing.

Stacked pull requests have to merge in order. When one branch was cut from another unmerged branch, merge the base first, or the second PR carries the first one's changes with it.
