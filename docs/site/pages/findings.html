Findings

How an analysis turns crawl, code, search and connector data into ranked findings, how History tracks a finding across runs, and how to add a new one. For where findings are produced in the run, see Site analysis.

The Finding type

Defined in packages/core/src/types.ts:94:

interface Finding {
  id: string;                 // createId("finding"), new every run
  siteId: string;
  analysisId: string;
  category: FindingCategory;
  severity: Severity;
  title: string;
  summary: string;
  evidence: JsonObject;
  organicImpactScore: number; // 0-100
  recommendation?: string;
  pagesAffected?: string[];
  createdAt: string;
}
Severity
CRITICAL, HIGH, MEDIUM, LOW, INFORMATIONAL
FindingCategory
rendering, sitemap, indexing, metadata, structured_data, internal_links, content, conversion, competitors, search, repository, ai_visibility

Findings are not stored in their own table. They live in the report, analyses.report_json under findings. When a report is too big for a D1 row, compactReport drops evidence beyond the top 10 findings first, then all evidence (packages/db/src/index.ts:330). Because id changes every run, anything that needs "the same finding" across runs uses findingKey instead (see History).

The category decides which dashboard area explains the finding: findingArea in apps/web/app/components/report-model.ts:104 sends search to Search, competitors to Competitors, conversion to Leads, ai_visibility to AI, and everything else to Technical.

Severity and organic impact

The rule in packages/core/src/severity.ts is that severity reflects expected organic business impact, not lint rules. Most producers compute an organicImpactScore and derive severity from it with severityFromImpact:

ScoreSeverity
90 and upCRITICAL
70 to 89HIGH
40 to 69MEDIUM
15 to 39LOW
under 15INFORMATIONAL

organicImpactScore(input) builds a score from facts about the problem. It starts at 10 and adds: 55 for empty shells at scale, 40 for blocking the crawl, 20 for commercial intent, 25 if more than half the traffic is affected (15 if more than a fifth), and pages affected divided by 100, capped at 20. rendering and indexing get 10 more. A metadata problem on fewer than 5 pages is capped at 25. The result is rounded and clamped to 0 to 100.

Not every producer uses that formula. The crawler's checks do, and the code findings do for client-rendered templates the crawl confirms (other code findings use fixed scores); the connector findings and conversion findings set impact directly with their own capped expressions (for example Math.min(90, 50 + Math.round(share * 0.4)) for an impressions fall). A few override severity outright: "robots.txt blocks Googlebot from the entire site" is always CRITICAL, and the AI crawler finding is always INFORMATIONAL with score 10, because blocking AI crawlers is a legitimate choice.

Ranking

rankSeverityByOrganicImpact (packages/core/src/types.ts:344) sorts by organicImpactScore descending, then by severity order for ties. The pipeline calls it once on all findings. The ranked list then feeds:

  • buildOpportunities (packages/agents/src/index.ts:69): every finding becomes a technical_enabler opportunity titled Resolve: <finding title>, with priority impact² / (50 × effort) (effort 4 for rendering, 2 otherwise). Squaring makes severity dominate.
  • synthesizeGrowthPlan: the titles of the top three findings scoring 40 or more become the plan's constraints, and any CRITICAL or HIGH finding puts "Fix the critical and high-impact technical findings" first in the strategy sequence.

How they are combined

All producers are pure functions that return Finding[]. runFullAnalysis in packages/agents/src/pipeline.ts:169 calls them in this order and pushes everything into one array:

  1. A rendering finding "Failed to fetch <url>" (MEDIUM, score 30) for any sampled page that could not be fetched.
  2. Crawl findings. findingsFromCrawl always runs on the sample. When a full crawl completed, its rendering and sitemap findings (and structured_data, when the crawl has per-issue counts) are dropped and findingsFromCrawlCoverage adds findings from every sitemap URL instead: evidence from the whole site supersedes extrapolation from a sample.
  3. findingsFromConversion.
  4. findingsFromCode, only when a repository was analysed.
  5. findingsFromRendering.
  6. runTechnicalSeoAudit, with fullCrawl set when the full crawl has per-issue counts, so it skips the per-page checks the crawl already covers (canonical mismatches, weak titles, thin descriptions).
  7. findingsFromSearch, only when there are Search Console rows.
  8. Connector findings: findingsFromCrawlLog (only with log coverage), findingsFromSearchConsoleImport, findingsFromTrends, then notFoundProbeFinding, then findingsFromInventory.
  9. rankSeverityByOrganicImpact(findings) at packages/agents/src/pipeline.ts:364.

Connector producers return [] when their input is null, so a site without that connector simply has none of those findings.

Related outputs that are not findings

  • Robots and AI readiness. packages/crawler/src/robots.ts is the robots.txt parser the producers use; it produces no findings itself. aiReadiness (packages/crawler/src/ai-readiness.ts:38) builds the report's aiReadiness section (per AI crawler allowed or not, llms.txt, FAQ markup) and the Results points; the ai_visibility finding comes from runTechnicalSeoAudit.
  • Competition and opportunities. packages/agents/src/competition.ts produces Opportunity objects, not findings: competitionOpportunities (line 265) turns content gaps into "Publish your <dataset> data as <label>" or "Build <label>: competitors have ~N, you have ...". buildOpportunities combines them with the Resolve: opportunities from findings, searchOpportunities (packages/agents/src/search.ts:273), unpublished-data opportunities, gapOpportunities from keyword lists, and linkGapOpportunity (packages/agents/src/connector-findings.ts:107), sorted by priorityScore.

History

The Dashboard's History tab shows which problems the analysis once reported are gone, and when. Three files split the work: pure logic in packages/core/src/history.ts, storage in packages/db/src/history.ts, and assembly for the tab in apps/web/src/history.ts.

findingKey

findingKey = `${category}|${title with every number run replaced by "#", trimmed, lowercased}`

Numbers (thousands separators included) are blanked so "waits for 3 requests" and "waits for 4 requests" are the same problem across runs (packages/core/src/history.ts:31).

The key is built from the title. Rewording a finding's title, or moving it to another category, makes every earlier occurrence look resolved and the new one look new in History. Changing only the numbers in a title is safe.

Key lists in site_snapshots

When an analysis completes, saveAnalysisReport calls saveFindingKeys (packages/db/src/history.ts:39). It writes one site_snapshots row with kind finding_keys, scope the analysis id, and rows from runKeys: one KeyRow per finding (id, key, title, category, severity, up to 50 pages). A list is a few KB, so History can diff runs without parsing reports.

Runs completed before key lists existed get theirs from their report on the next History open: historyRuns backfills up to BACKFILL_RUNS (12) missing lists per open, newest first, with an insert that never replaces a list a finishing run just saved. Their crawls are long pruned, so backfilled lists have no vanished rows.

Vanished

A finding can stop being reported because it was fixed, or because the pages it pointed at no longer exist. runKeys adds a vanished: true row for each previous-run finding that this run does not report, that had at least one page, and whose pages are all in vanishedPages. vanishedPages (packages/db/src/history.ts:28) returns, of up to 500 URLs, those that were live in the previous crawl (fetched, status under 400) and are missing or erroring (400 or more) in this one. A page the previous crawl never fetched is unknown, never vanished.

This is decided at save time, not when History is opened, because pruneCrawlResults keeps crawl rows for only the latest two completed runs. That is why saveAnalysisReport saves the key list before it prunes.

Resolutions

resolutions(runs) (packages/core/src/history.ts:52) walks the runs oldest to newest. A key that was open and is absent from a run becomes a Resolution with firstSeen (the earliest consecutive run that reported it), resolvedAt and resolvedBy (the first run without it), and vanished if that run carries a vanished row for the key. If a later run reports the key again, the earlier resolution gets reopenedAt and a new open stretch starts. It also returns how many keys are still open.

assembleHistory (apps/web/src/history.ts:23) labels each resolution:

  • fixed: a change with status merged or pr_opened, whose findingId maps (through the key lists) to this key, was created between firstSeen and resolvedAt. Changes record the finding id they were generated from (apps/web/app/api/analyses/[analysisId]/changes/route.ts).
  • vanished: "Every page it pointed at is gone or erroring, so it no longer applies."
  • resolved: "The analysis stopped reporting it."

Those rows are merged with Eumon's actions (changes, page edits, CTA tests, publications), sorted newest first and capped at 200.

Adding a new finding

The most recent producers, the trend findings (commit 2369710) and the inventory findings (commit d79d900), were added this way.

  1. Pick the home. A check on crawl data goes in packages/crawler/src next to the existing crawl producers; a check on connector data goes in packages/agents/src/connector-findings.ts. If an existing producer already reads the data you need, add a draft to it rather than writing a new function.
  2. Load the input, if it is new. Write a loader that reads D1 and returns a plain signal type, for example loadTrendSignals in packages/agents/src/trend-signals.ts or loadInventories in packages/agents/src/inventory-data.ts. Add the signal as an optional field on ConnectorSignals (packages/agents/src/connector-findings.ts).
  3. Write a pure producer. findingsFromX(input): Finding[] that returns [] when the input is null. Follow the file's pattern: collect Drafts (category, impact, title, summary, evidence, recommendation, pages), keep thresholds in a named constant with the reason for each (see TREND and INVENTORY), cap impact with Math.min, then map drafts to findings with createId("finding") and severityFromImpact(impact).
  4. Choose the category. It decides the dashboard area (findingArea) and is part of the History key. A new category means adding it to FindingCategory in packages/core/src/types.ts and to findingArea if it belongs outside Technical.
  5. Write the title for History. Put counts in the title freely (they are blanked in the key), but keep the wording fixed: a title whose words change with the data becomes a different key every run.
  6. Test it. Add cases to the sibling test file (for example packages/agents/src/connector-findings.test.ts, node:test with assert/strict): the finding fires above the threshold and stays quiet below it.
  7. Call it in the pipeline. Push its findings in runFullAnalysis before rankSeverityByOrganicImpact (packages/agents/src/pipeline.ts:364), reading its input from input.connectors or another RunAnalysisInput field.
  8. Feed it from the Workflow. In the analyze-repository-and-site step of apps/web/src/analysis-workflow.ts, load the signal and pass it through connectorSignals (apps/web/src/connectors-data.ts:44). Wrap the load in .catch: connector data is an enrichment and must never fail an analysis. If the load is heavy, give it its own step, as the inventory has.
  9. Feed the demo. analyzeDemo in packages/agents/src/demo.ts builds its own connectors object instead of calling connectorSignals, so add the signal there too. The inventory commit also seeded demo data that triggers its finding, and the trend findings got a follow-up commit (ee74395) to make the demo slow enough for the crawl-pace finding.
