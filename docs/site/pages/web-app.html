Web app

Reference for apps/web: the dashboard's views and the components behind them, every API route, the shared server helpers, the public routes, and how access is controlled today. Use it to find where a screen or an endpoint lives.

An accounts and security-hardening branch is in progress and will change access control, route guards and sign-in. This page describes main as of 2026-10-10.

The dashboard

The whole operator console is one client component, apps/web/app/page.tsx, rendered at /. It loads the site list from GET /api/sites, keeps the selected site, view, tab and Ask thread in the query string (?site=…&view=…&tab=…&thread=…) so a refresh or shared link lands on the same place, and switches views in place without route changes. The client API helper

Every dashboard call goes through api() in apps/web/app/components/api.ts:10:

  • api<T>(path, init) calls fetch with cache: "no-store". Passing json in init serialises it and sets Content-Type: application/json.
  • On a non-2xx response it throws ApiError, carrying the server's { error } message (or Request failed (status)) and the status.
  • errorMessage(error) turns anything caught into a display string.

The same file has the formatting helpers formatNumber, formatDay and percent. The one call that does not use api() is the Ask stream (POST /api/sites/:siteId/assistant), which reads server-sent events with a raw fetch in Ask.tsx.

How analysis progress is polled

apps/web/app/components/AnalysisProgress.tsx polls GET /api/analyses/:analysisId/progress outside React, in a module-level watches map, so polling continues when the user leaves the Dashboard.

  1. watch() starts a loop for one analysis and drops any older watch for the same site.
  2. Each tick fetches the progress route and notifies subscribers; components read it with useRun or useSiteRun (both useSyncExternalStore).
  3. The next tick is 2.5 seconds later, or 15 seconds when the run is reported stalled. A 404 ends the loop.
  4. When the status is completed, failed or cancelled, the loop stops, the tab title changes, and a browser notification fires if the user allowed them.
  5. While polling, the tab title shows the stage or crawl percentage, and the top bar shows a run chip on other views.

The progress route (apps/web/app/api/analyses/[analysisId]/progress/route.ts) returns the job's status, stored progress and stage history, whether it is stalled, and crawl counts with pace and time left. For the demo site it advances the simulated run on each poll. How the workflow writes that progress is on Analysis flow.

"Sync now" is polled separately: OverviewView.tsx checks the sync record every four seconds for up to fifteen minutes and asks GET /api/sites/:siteId/results/sync?id=… for the Workflow instance status. See Results sync flow.

Shared server helpers

apps/web/src/server.ts holds the helpers most routes use:

json(data, status = 200)
JSON response with Cache-Control: no-store.
fail(message, status = 400)
{ error: message } with no-store. This is the shape api() reads on the client.
readText(request, maxBytes), readJson(request, maxBytes = 64 KB)
Read a body without trusting Content-Length; return null when it is too large or not a JSON object.
appLlm()
The configured model from createLlm, or a 503 response explaining how to configure one.
llmFailure(error)
Turns a model error into a 502 or 503 with an actionable message.
settingsFor(site), prettySiteName(site)
The site's page settings, or defaults built from its name and URL.
isPublicHttpUrl(value)
A URL string of at most 2048 characters that passes the crawler's isSafePublicUrl.

Some older routes call Response.json directly with the same { error } shape. Other server-side modules in apps/web/src/ back specific routes: public-pages.ts (landing pages), share.ts (share tokens), crawl-logs.ts (log ingest), gsc-auth.ts (Google tokens), results-data.ts and results-access.ts (Results payload and keys), and the three Workflow files.

Public routes

Landing pages: /p/:siteId/…

apps/web/app/p/[siteId]/[[...path]]/route.ts exports GET, HEAD and POST. It looks up the site (404 if unknown) and hands off to apps/web/src/public-pages.ts:

  • servePublicGet (apps/web/src/public-pages.ts:86) serves, under the site's mount path: a health check at /__eumon/health, the IndexNow key file, sitemap.xml, robots.txt (only when there is no mount path), the hub page, and each published page. Unpublished or retired pages return 410.
  • Responses carry X-Robots-Tag: noindex unless the request came through the customer's proxy (X-Eumon-Proxy: 1 or a matching X-Forwarded-Host).
  • POST is accepted only on the beacon path /__eumon/e: servePublicBeacon records page views and CTA clicks from the rendered page's inline script, with first-touch session attribution through the eumon_sid cookie.

The full flow from dataset to served page is on Landing page flow.

Conversion events with CORS

apps/web/app/api/sites/[siteId]/events/route.ts receives events from the tracking snippet (from GET /api/sites/:siteId/integration) or from @organic-growth/sdk.

  • OPTIONS and POST accept a request only when its Origin is the same site as the site's baseUrl or its landing-page publicOrigin (www and apex count as one). Otherwise 403.
  • The allowed origin is echoed in Access-Control-Allow-Origin with Vary: Origin; preflight allows POST, OPTIONS and Content-Type, cached for a day.
  • The body is capped at 4096 bytes, the event name must be one of a fixed list (page_view, cta_click, whatsapp_click, form_submit and others), and pageUrl must be on the allowed origin. A whatsapp_click with a reference code also records a lead click.
  • It answers 202 { accepted: true }.

Client share link: /r/:token

apps/web/app/r/[token]/page.tsx renders ClientReport, which loads GET /api/r/:token and shows the Results sections read-only, without site health, AI readiness checks or controls. The token is signed with SESSION_SECRET, carries purpose: "results", the site ID and the site's share version, and lasts five years (apps/web/src/share.ts). Revoking bumps the share version, which invalidates every earlier token.

PWA files

apps/web/public/ holds manifest.json and the icons, referenced from apps/web/app/layout.tsx, so the dashboard can be installed as a standalone app. public/sw.js is a retired service worker: nothing registers it any more, and its only job is to clear the old offline cache and unregister itself in browsers that installed an earlier version.

Access control

On main the app has no user accounts, no sign-in and no middleware. Operator routes do not check who is calling. The intended protection is Cloudflare Access in front of the hostname, configured in Cloudflare, not in this repo (apps/web/README.md, "Access control").

The README lists the paths that must be excluded from Access, or landing pages and tracking stop working:

  • /p/*: landing pages, sitemap and the analytics beacon.
  • /api/sites/*/events: conversion events from customer sites.
  • /r/* and /api/r/*: client Results links (signed, revocable tokens).

What the code itself checks today:

  • Event ingestion checks the request Origin against the site (above).
  • /api/logs/:siteId checks a per-site token derived from SESSION_SECRET (Bearer header or ?token=) and gives the same 401 for an unknown site and a wrong token (apps/web/src/crawl-logs.ts:21).
  • Share links are verified by signature, purpose and share version.
  • OAuth and GitHub install flows check signed state or a state cookie.
  • /api/dev/demo-site refuses non-local requests in a production build.

/api/logs/:siteId is called by Cloudflare Logpush, Vercel or the log-forwarding Worker, none of which can pass Cloudflare Access, and it is not in the README's exclusion list. If log delivery is used behind Access, that path needs excluding too; it relies on its own token.

See Gotchas for other things that bite during setup, and Ops for deploying.
