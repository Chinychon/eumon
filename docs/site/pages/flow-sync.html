The daily Results sync

How Eumon refreshes every site's Results numbers once a day, or on demand from "Sync now": the cron trigger, the per-site workflow, each data source and what it writes, the URL Inspection budget, and how a run is recorded and reported back to the dashboard.

Cron 15 4 * * * (04:15 UTC), or POST /api/sites/:siteId/results/sync
Workflow
SearchSyncWorkflow, binding SEARCH_SYNC_WORKFLOW, name search-sync
Unit of work
One workflow instance per site
Main code
apps/web/src/sync-steps.ts, apps/web/src/results-sync.ts, apps/web/src/results-sources.ts, apps/web/src/connector-sources.ts, apps/web/src/url-inspection.ts
Record
One row in sync_runs per run, with every note

From cron to one instance per site

The Worker declares one Cron Trigger in apps/web/cloudflare.config.ts: triggers.scheduled({ schedule: "15 4 * * *" }). The comment there explains the choice: a Cron Trigger is available on the Workers Free plan, while Workflow schedules would need the paid plan.

The cron runs the scheduled handler in apps/web/worker.ts, which calls startDailySyncs(env, new Date(controller.scheduledTime)) inside ctx.waitUntil. startDailySyncs (apps/web/src/sync-steps.ts:212) lists every site with listSitesForResults (all rows of sites, since speed and authority need no connection) and calls startSync for each with trigger: "daily".

Instance ids are deterministic (apps/web/src/sync-steps.ts:173):

  • Daily: daily-<YYYY-MM-DD>-<siteId>, the UTC day of the scheduled time. A second firing on the same day tries to create the same id, Cloudflare refuses, and startSync treats an instance it can fetch as "already exists". So a repeated cron creates nothing.
  • Manual: manual-<siteId>-<window>, where window is the current time rounded down to a 10-minute boundary in epoch milliseconds (MANUAL_WINDOW_MS). Clicks of Sync now within the same 10 minutes join one run.

Each site gets its own instance so each has its own budget of 1,024 workflow steps (comment at the top of sync-steps.ts).

"Sync now" and the 409

apps/web/app/api/sites/[siteId]/results/sync/route.ts has two handlers:

POST
Needs a signed-in Owner or Member of the site's workspace (requireSite with write; a Client gets 403). Calls startSync(env, { siteId, trigger: "manual" }) and answers 202 with { id, startedAt, joined }. startedAt is the start of the 10-minute window, and the run record uses the same value. joined is true when the click landed in a window whose instance already exists. If the site's daily-… instance for today is still in flight (status queued, running, paused, waiting or waitingForPause), no manual instance is created and the route answers 409. This stops the two runs spending the day's inspection quota twice. A failure to create the instance answers 503.
GET ?id=…
Returns { status, error } for one instance. The id must start with manual-<siteId>- or end with -<siteId>, otherwise 404. An instance that can't be fetched comes back as status: "unknown".

A separate route, apps/web/app/api/sites/[siteId]/search-sync/route.ts, runs only the generated pages' Search Console import (syncGeneratedPageSearch) directly in the request, without a workflow. The Page results view calls it. It answers 409 when the site has no Search Console property.

Inside one instance

SearchSyncWorkflow.run (apps/web/src/search-sync-workflow.ts) builds the dependencies (D1, Google access for the site, API keys from the environment, the page-search import) and hands them to syncSite (apps/web/src/sync-steps.ts:60). Every step is named <siteId>/<name>. Each step is wrapped so that a step that still fails after its retries adds a note and the run continues.

  1. start: loads the site. If the site is gone the run notes skipped: site removed. For a site with a Search Console property (and not the demo site) it also counts the inspections already spent since midnight Pacific and the number of published Eumon pages.
  2. page-search (only with a property and at least one published page): syncGeneratedPageSearch imports the last 28 days of Search Console data for pages under Eumon's mount path. See Sources.
  3. sources: syncResults runs every source but DataForSEO's (OTHER_SOURCES) in order, in one step, with one retry after 60 seconds. The step first trims the API keys to what the site's workspace may spend (below).
  4. dataforseo-limits, dataforseo (only with a DataForSEO key, and when the workspace may spend it): syncResults runs the five DataForSEO sources (DATAFORSEO_SOURCES) in a step of their own with the same retry, so neither step passes the Free plan's 50 subrequests (on a worst-case Monday, 27 and 31). Rank tracking and AI answers follow.
  5. pages-1, pages-2, …, index-counts, coverage-queue, coverage-1, …: URL inspections, skipped when the notes already contain google failed. See URL Inspection.
  6. record: writes the run to sync_runs. A failure here doesn't fail the sync.

The workflow returns { [siteId]: notes.join("; ") }.

Sources

syncResults (apps/web/src/results-sync.ts:53) walks the SOURCES array (apps/web/src/results-sources.ts:307, which ends with CONNECTOR_SOURCES from apps/web/src/connector-sources.ts:295). For each source the runner:

  • skips it silently when applies is false (no property, no key);
  • for Google sources, connects to Google once per sync. If connecting fails it notes google failed: … once and skips every later Google source;
  • adds the source's skip note if it has one (for example speed: no Google API key);
  • works out whether this is a first run: a source with a marker metric that has no point yet is on its first run, which backfills;
  • runs weekly sources only on Mondays (UTC), unless it is their first run;
  • writes the returned points to metric_points, plus a marker point (value = points written) when the source has a marker;
  • turns a throw into a <name> failed: … note.

metric_points is the Results ledger: one value per site, metric and day, upserted on (site_id, metric, day) so re-runs and Search Console revisions overwrite rather than double count (packages/db/src/metrics.ts:13). Lists that replace themselves (keyword lists, results pages, link profiles) go to site_snapshots, one row per site, kind and scope (packages/db/src/snapshots.ts).

On the demo site only the first-party source runs, because its data is seeded and the domains are fictional.

Every key above is read in signalKeys (apps/web/src/results-access.ts:9); a blank secret counts as no key. Google OAuth uses the site's stored credential, refreshed with GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET and OAUTH_ENCRYPTION_KEY (googleAccess, same file).

DataForSEO costs money per call, so it is a per-workspace feature. The dataforseo step runs only when the site's workspace limits have dataForSeo on, and both source steps remove the DataForSEO key otherwise before calling syncResults (keysForLimits, apps/web/src/limits.ts:62). The five DataForSEO sources (competitor keywords, keyword volumes, search competitors, search results, backlinks) then don't apply and are skipped silently. A site with no workspace_id gets the free limits, so it never spends DataForSEO either (apps/web/src/sync-steps.ts:99). The free limits leave dataForSeo off; the initial workspace has it on.

The page-search step before the sources writes to two tables, not the ledger: page × query totals replace the site's rows in page_search_metrics, and page × day clicks and impressions are upserted into the search_clicks and search_impressions columns of page_metrics_daily (apps/web/src/search-sync.ts).

The older search_metrics table is not written by this sync. It is replaced by the analysis workflow and by choosing a Search Console property (replaceCurrentSearchMetrics).

Cloudflare has no optional secrets: every secret declared in cloudflare.config.ts, including the optional source keys, must be set before a deploy (comment in that file). A keyed source runs only when signalKeys finds a non-blank value for its key.

URL Inspection

Google allows 2,000 URL inspections per property per day (DAILY_QUOTA, apps/web/src/sync-steps.ts:38), and the quota day starts at midnight in Los Angeles. pacificDayStart computes that instant, and the start step counts what is already spent with countInspectionsSince (packages/db/src/coverage.ts:95): rows of url_index_status plus rows of page_index_status whose checked_at is on or after it. The stored inspections are the quota ledger, so a manual run after the daily one sees what the daily run spent.

Only sites with a Search Console property inspect, and never the demo site. The work is split into steps of 40 inspections (INSPECTION_STEP, apps/web/src/url-inspection.ts:8) so a step, with its token refresh, stays under the Free plan's 50 subrequests per step. Inside a step, URLs are asked 10 at a time. Each inspection step gets one retry after 30 seconds and a 3-minute timeout.

  1. Eumon pages: up to 100 published pages a day (PAGE_INSPECTIONS_PER_DAY), never-checked first, then the oldest check, skipping pages already checked today. Results go to page_index_status. A page Google fails on is still saved, with verdict VERDICT_UNSPECIFIED and the error text as its coverage state, so it counts as "not checked yet" and is not asked again until the next day.
  2. Index counts: if any page was inspected, pages_indexed and pages_not_indexed are written to the ledger for today.
  3. Coverage queue: read once, in its own step, by urlsToInspect (packages/db/src/coverage.ts:19). It takes the latest completed crawl's served URLs: never-checked ones first, taken in turn from each page type, then URLs last checked more than 30 days ago. Its size is the smaller of 1,880 (COVERAGE_URLS_PER_DAY) and what is left of the quota after the pages.
  4. Coverage steps: the queue is inspected 40 per step into url_index_status. A URL Google won't inspect (for example one outside the property) is saved with verdict ERROR, so it waits 30 days like a checked URL.

A refusal that holds for the day stops inspection: 429 (quota), 401 (revoked token), or a whole batch of 10 answering 403. Nothing is saved for a refused batch, and the run notes inspection stopped: Google answered … or coverage stopped: ….

Two different "days" are in play. The quota count starts at Pacific midnight; the "already checked today" filter for Eumon pages and the ledger day for index counts use the UTC date of the run's start.

Sync runs and notes

The last step writes one row to sync_runs (recordSyncRun, packages/db/src/activity.ts:14): id, site, trigger (daily or manual), started_at, finished_at and notes_json. Each site keeps its latest 30 runs; older rows are deleted in the same batch.

Notes are plain strings, one per thing that ran or didn't: search: 7 days, speed: no Google API key, quota: 1,200 inspections already today, 800 left, coverage: inspected 400 in 10 steps, bing failed: …. A note is a problem when it contains the word failed, stopped or refused (isProblemNote, packages/core/src/sync-notes.ts:2).

GET /api/sites/:siteId/sync-runs (apps/web/app/api/sites/[siteId]/sync-runs/route.ts) returns listSyncRuns: the latest 20, newest first, with Cache-Control: no-store. Setup → Sync history shows them.

How the dashboard knows a sync finished

The Sync now button in apps/web/app/components/OverviewView.tsx posts to the sync route, then runs waitForSyncRun: every 4 seconds, for up to 15 minutes, while the view is open, it:

  1. fetches /sync-runs and looks for a manual run whose startedAt is at or after the startedAt the POST returned. Found means finished: the view reloads Results and, if any notes are problem notes, shows them as "Sync finished, but N sources didn't update";
  2. otherwise asks GET /results/sync?id=… for the instance status. errored or terminated ends the wait with "Sync failed".

A failed poll is ignored and retried on the next tick. After 15 minutes the view says the sync is still running and points to Sync history.

A POST that returns 409 (today's daily run is still in flight) surfaces as an error in the view. Its result appears in Sync history as a daily run, which waitForSyncRun does not count.
