How code reaches production

There is no wrangler.toml or wrangler.jsonc in the repo. The Worker is described in apps/web/cloudflare.config.ts with cf/config, and deployed by the cf CLI through vinext-cloudflare deploy (the deploy script in apps/web/package.json).

Production deploys through Cloudflare Workers Builds, connected to the GitHub repository. A merge to main starts a build. The two commands configured in the Worker's Settings, Builds section are:

SettingValueWhy
Build commandnpm run buildThe root script builds every package under packages/*, then the web app (package.json).
Deploy commandnpm run deploy -w @organic-growth/web -- --skip-buildRuns vinext-cloudflare deploy inside apps/web, skipping the build that already ran. It reads the CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID that Workers Builds injects.

The default deploy command, npx wrangler deploy at the repo root, fails with "The Cloudflare application detection logic has been run in the root of a workspace instead of targeting a specific project." Wrangler finds no config at the root, and the app is not a wrangler project anyway. Keep the deploy command above.

A Workers Builds deploy runs in strict mode. If someone changed the Worker in the Cloudflare dashboard and its settings now differ from cloudflare.config.ts (a plain-text variable where the config declares a secret, for example), the deploy stops with "Aborting the upload operation because of conflicts". Keep settings in the config and secrets as Secrets, never in the dashboard (apps/web/README.md).

The Worker's name appears three more times in the config: as the worker of each Workflow binding (ANALYSIS_WORKFLOW, SCRAPE_WORKFLOW, SEARCH_SYNC_WORKFLOW). Renaming the Worker means changing all four, or the deploy fails on the name.

Preview URLs and Builds for Preview branches

The config sets previewUrls: false (apps/web/cloudflare.config.ts:9), so Cloudflare does not serve each uploaded version at its own preview address. The app answers only on workers.dev and any custom domain you add. The workers.dev address stays on: it is the production URL.

Builds for Preview branches is a different switch, under Settings, Builds, and it is on for a new Worker. With it on, every push to a branch other than main runs the Preview command npx wrangler preview, which stops with "Your Wrangler configuration is missing a previews block". The result is a failing "Workers Builds: eumon" check on every pull request. defineWorker in cf/config has no previews option, and a preview would need its own D1, AI, Browser, Workflow bindings and secrets in any case. Turn the toggle off; builds of main are not affected.

Deploying by hand

From the repository root, after npm exec -w @organic-growth/web -- cf auth login (or with CLOUDFLARE_API_TOKEN exported):

npm run db:migrate:remote   # only if packages/db/migrations gained a file
npm run deploy              # builds the packages, then vinext-cloudflare deploy

To deploy your own copy, set CF_D1_DATABASE_ID to your database and change the ID in the two db:migrate:* scripts in apps/web/package.json.

One-off setup for accounts

Sign-in, workspaces and the GitHub ownership check need settings outside the repo. Do these once per Cloudflare account and production origin, before the first deploy that includes migration 0024. <origin> below is the production URL, for example https://eumon.chin-gabriel.workers.dev.

  1. Secrets. Set BETTER_AUTH_SECRET (openssl rand -hex 32, not the same value as SESSION_SECRET), BOOTSTRAP_OWNER_EMAIL, TURNSTILE_SITE_KEY, TURNSTILE_SECRET_KEY, GITHUB_APP_CLIENT_ID and GITHUB_APP_CLIENT_SECRET on the Worker (commands under Secrets). The deploy fails while any declared secret is missing.
  2. Google. In the Google Cloud OAuth client, add the redirect URI <origin>/api/auth/callback/google for sign-in, next to the existing <origin>/api/google/callback for the Search Console connection. Without it, Google refuses sign-in with redirect_uri_mismatch.
  3. GitHub App. Turn on Request user authorization (OAuth) during installation; GitHub then returns installers to the App's Callback URL, so set that to <origin>/api/github/callback. Copy the Client ID and a new client secret into GITHUB_APP_CLIENT_ID and GITHUB_APP_CLIENT_SECRET. Under Organization permissions, set Members to Read-only: an install on an organization is accepted only from one of its admins, and the check reads the installer's membership (apps/web/src/github-install.ts:33).
  4. Turnstile. Create a widget for the production hostname in the Cloudflare dashboard and use its site key and secret key. It only shows on the sign-in page once email sign-in is on, but both secrets must exist for the deploy.
  5. Rate limit namespace. AUTH_RATE_LIMIT is declared with namespace: "1001" (apps/web/cloudflare.config.ts:77). The namespace ID must be unique within the Cloudflare account; if another Worker in the account already uses 1001, change it here before deploying.
  6. Migration 0024. Run npm run db:migrate:remote before (or with) the deploy. It creates the Better Auth tables, the initial workspace ws_initial with no limits, and moves every existing site and GitHub installation into it (packages/db/migrations/0024_accounts.sql).
  7. Sign in. Sign in with Google as an address in BOOTSTRAP_OWNER_EMAIL. You become Owner of the initial workspace and see the existing sites, plus an Admin link.

Existing repository connections keep working, because the migration copies each site's installation into the initial workspace. Connecting a new installation goes through the ownership check, so if step 3 is skipped, Connect GitHub ends with an error naming the missing setting (apps/web/app/page.tsx:112).

Remote migrations

Workers Builds does not apply migrations. Whoever merges a pull request that adds a file to packages/db/migrations runs this before (or with) the deploy:

npm run db:migrate:remote

It runs cf d1 migrations apply 591e4045-cbff-4ef4-a894-cbe4ece424ec --dir ../../packages/db/migrations from apps/web. Applied migrations are recorded in the d1_migrations table and skipped on the next run. Code that reads a new table or column fails in production until its migration has run, so apply first, then deploy.

To see which migrations production has not applied yet, use the same cf form (it takes the database ID, not the name):

cd apps/web
npx cf d1 migrations list 591e4045-cbff-4ef4-a894-cbe4ece424ec --dir ../../packages/db/migrations

wrangler d1 migrations list eumon-prod --remote does not work here: wrangler reads the database's migrations_dir from a wrangler config with a d1_databases entry, and the repo has none. Use the cf command above, or query the table directly: npx wrangler d1 execute eumon-prod --remote --command "SELECT name, applied_at FROM d1_migrations ORDER BY id".

Some migrations drop tables (0009_drop_unused_tables.sql) or move data (0016_site_snapshots.sql, 0024_accounts.sql). A dropped production table cannot be restored by re-running anything. Read a migration before applying it remotely.

Schema and table descriptions live on Data model.

Every value the Worker reads besides its bindings is declared with bindings.secret() in apps/web/cloudflare.config.ts. Cloudflare has no optional secrets: each declared secret must exist on the Worker before a deploy, even for features you do not use.

ANTHROPIC_API_KEY and LLM_MODEL are deliberately left undeclared so they stay optional; set them on the Worker directly. The provider order (DeepSeek, then Claude, then Workers AI) is described in Packages. The email flags are undeclared for the same reason: EMAIL_ENABLED=true and EMAIL_FROM turn on magic-link sign-in and email verification, and PASSWORD_SIGNIN=true adds passwords on top. Both need Workers Paid: sending email to any address does, and password hashing exceeds the Free plan's CPU limit (apps/web/src/passwords.ts:3).

Two bindings need no value but are part of the config: EMAIL, Cloudflare's send-email binding, and AUTH_RATE_LIMIT, 10 attempts a minute per IP address on every non-GET request to /api/auth/* (apps/web/worker.ts:35).

npx wrangler secret put SESSION_SECRET --name eumon      # prompts for the value
npx wrangler secret list --name eumon
# or, with the cf CLI installed in apps/web:
npx cf workers secrets update SESSION_SECRET --worker eumon --text '...'
npx cf workers secrets list --worker eumon

Adding a new bindings.secret() to the config means setting it on the production Worker before the next merge to main, or that deploy fails.

Workspaces, /admin and limits

Every site belongs to a workspace. A new workspace gets the free limits in apps/web/src/limits.ts:18: one site, 3 analyses, 500 scraped pages, 20 Ask Eumon questions and 10 AI writing runs a day, 3 people (members, clients and pending invitations together), and no DataForSEO, pull requests or Google Sheets export. Daily counters reset at midnight UTC. A refused action answers with a sentence saying what to do: 429 when a daily allowance or the site limit is used up, 403 for a feature the workspace does not have, and 400 from the invitation route when the people limit is reached (apps/web/app/api/workspace/invitations/route.ts:27). The initial workspace has no limits. Roles are described in Access control.

/admin lists every workspace with its site count, people and today's usage against each limit, and saves new limits per workspace. Only signed-in users whose verified email is in BOOTSTRAP_OWNER_EMAIL can use it; anyone else gets "Not found." (apps/web/src/guard.ts:59). An empty number field means unlimited.

The page calls two routes, which you can also use from a terminal (see Observability for the cookie and Origin header):

  • GET /api/admin/workspaces: the free defaults and every workspace with its usage and overrides.
  • PUT /api/admin/workspaces/<workspaceId>/limits: the JSON body is merged into the workspace's overrides in workspace_limits (apps/web/app/api/admin/workspaces/[workspaceId]/limits/route.ts:24). Limits left out keep their value, so {"sites": 5} changes only the site limit. A value equal to the free default is dropped rather than stored, so the workspace follows FREE_LIMITS if that changes. Numbers are whole numbers or null (unlimited); features are true or false; unknown keys are dropped.

The cron trigger

The daily Results sync is a Worker Cron Trigger, triggers.scheduled({ schedule: "15 4 * * *" }) (apps/web/cloudflare.config.ts:12). At 04:15 UTC Cloudflare calls scheduled in apps/web/worker.ts:52, which runs startDailySyncs (apps/web/src/sync-steps.ts:212): one search-sync Workflow instance per site, with the ID daily-<YYYY-MM-DD>-<siteId>. Because the ID is fixed for the day, a second firing creates nothing. The cron does not pass through the sign-in gate. "Sync now" creates manual-<siteId>-<window> instances through POST /api/sites/<siteId>/results/sync; clicks within ten minutes join one run, and a click while that day's daily run is in flight gets a 409.

Workflow schedules are not used because they need the paid plan; cron triggers are accepted on Free. The sync itself is described in the sync flow.

Observability

Wrangler is not a dependency of this repo; npx wrangler fetches it, and npx wrangler login signs in. None of the commands below need a wrangler config: each names the Worker, Workflow or database.

Live logs

npx wrangler tail eumon --format json

Streams every request, cron firing and Workflow step invocation with its console output, exceptions and outcome (for example exceededCpu). Use --format pretty for a quick look; JSON keeps the full exception text. While email is off, sign-in, verification and invitation emails are written here instead of being sent (apps/web/src/auth.ts:31).

Workflows

npx wrangler workflows list
npx wrangler workflows instances list site-analysis
npx wrangler workflows instances describe site-analysis <instance-id>

describe shows every step with its start and end time, retries, output and error. It is the quickest way to see which batch a crawl stopped on and with what message. Instance IDs:

WorkflowInstance IDCreated by
site-analysisThe analysis ID (analysis_…)apps/web/app/api/sites/[siteId]/analyses/route.ts:59
dataset-scrapeThe scrape job IDapps/web/app/api/datasets/[datasetId]/scrape/route.ts:32
search-syncdaily-<day>-<siteId> or manual-<siteId>-<window>apps/web/src/sync-steps.ts:191

Analysis steps are named load-site, enqueue-full-crawl, crawl-batch-<n>, research-<domain>, inventory, analyze-repository-and-site and so on (apps/web/src/analysis-workflow.ts; walkthrough in the analysis flow).

D1 usage

npx wrangler d1 info eumon-prod
npx wrangler d1 insights eumon-prod --sort-by reads --timePeriod 1d --json

d1 info prints the database size and the rows read and written in the last 24 hours: compare those with the Free plan's daily limits before starting a large crawl. d1 insights lists queries with their total and average rows read, so a query that walks a whole table stands out at the top.

Calling the API from a terminal

Every API route outside the public list needs a session: without one the gate answers 401 (apps/web/src/gate.ts:25), and the route then checks your role on the site. Sign in in a browser, copy the session cookie from the developer tools (__Secure-better-auth.session_token on HTTPS, better-auth.session_token on http://localhost), and pass it with -b. Anything other than GET, HEAD or OPTIONS also needs an Origin header equal to the app's own origin, or it is refused with 403 (apps/web/src/gate.ts:29).

APP=https://eumon.chin-gabriel.workers.dev
COOKIE='__Secure-better-auth.session_token=<value>'
curl -s -b "$COOKIE" "$APP/api/analyses/<analysisId>/progress"
curl -s -b "$COOKIE" -H "Origin: $APP" -X POST "$APP/api/analyses/<analysisId>/cancel"

That cookie is a full sign-in for your account for up to 30 days (apps/web/src/auth.ts:74). Keep it out of shell history and shared notes, and sign out in the browser when you are done, which ends the session.

An analysis's own view

GET /api/analyses/<analysisId>/progress returns status, the stage timeline in progress, error, crawl counts with pace and time left in crawl, and stalled (apps/web/app/api/analyses/[analysisId]/progress/route.ts). stalled becomes true when a queued or running analysis has not updated its progress for 45 minutes (packages/db/src/index.ts:209); the dashboard then lets a new run start.

Sync results are recorded per run: GET /api/sites/<siteId>/sync-runs returns the last 20 with each source's notes (Setup, Sync history in the dashboard). GET /api/sites/<siteId>/results/sync?id=<instance-id> returns a sync instance's Workflow status and error.

Runbook

An analysis looks stuck

  1. Read /api/analyses/<id>/progress (in the browser while signed in, or with curl and your session cookie). Note the last stage, progress.updatedAt, and stalled.
  2. Run npx wrangler workflows instances describe site-analysis <id>. If the instance is errored or terminated while the record says running, the Workflow died without closing the record: its catch block writes failed to D1 (apps/web/src/analysis-workflow.ts:209), and that write fails when D1 is unavailable or the invocation has used up its Cloudflare API calls.
  3. If the instance is still running, look at the current crawl-batch-<n> step's retries and error, and at wrangler tail for exceptions.
  4. Close the record with Cancel in the dashboard, or POST /api/analyses/<id>/cancel with your session cookie and the Origin header. Cancel needs Owner or Member rights on the site, terminates the instance if it still exists, and marks the analysis cancelled.

Every route returns 500

  1. Check whether the routes that fail are the ones that touch D1. Static assets still load. Sign-in and every signed-in page can fail too: the session lives in D1, and the signed cookie copy that saves the lookup only lasts five minutes (apps/web/src/auth.ts:77).
  2. Run npx wrangler d1 info eumon-prod. If rows read in the last 24 hours are near 5 million (or rows written near 100,000), the D1 Free daily limit has been hit. Nothing in the app is broken: D1 refuses queries until the limit resets at 00:00 UTC.
  3. Find what spent the budget with npx wrangler d1 insights eumon-prod --sort-by reads --timePeriod 1d --json, and fix that query before the next large run (see Query-plan traps).
  4. If D1 is fine, npx wrangler tail eumon --format json and reload a failing page to read the exception.

A sync failed

  1. Read Setup, Sync history (or GET /api/sites/<siteId>/sync-runs). Each run lists one note per source; a failing source says why.
  2. If the run never landed there, find the instance: npx wrangler workflows instances list search-sync, then npx wrangler workflows instances describe search-sync daily-<day>-<siteId>. Read the failed step's error; "Too many subrequests" is the Free plan's 50-subrequest cap.
  3. A quota: note reports how much of Google's URL Inspection quota (2,000 per property per Pacific day, apps/web/src/sync-steps.ts:38) was already spent that day. When it is spent, inspections wait for the next Pacific day.
  4. No DataForSEO results while the keys are set means the site's workspace does not have the DataForSEO feature: the sync drops those keys for it (apps/web/src/sync-steps.ts:93). Turn it on in /admin.
  5. Start a new run with Sync now. A click while that day's daily run is in flight returns 409; wait for it.

Someone cannot sign in

  • Google shows redirect_uri_mismatch. The OAuth client is missing <origin>/api/auth/callback/google (One-off setup, step 2).
  • "Too many attempts. Wait a minute, then try again." The AUTH_RATE_LIMIT binding refused the request: more than 10 sign-in requests from that IP address in a minute. It clears by itself.
  • Signed in, but sees "You don't have a workspace yet". They signed up while an invitation was pending and it expired before they accepted it, so no workspace was made for them. The button on that page creates one; or send a new invitation.
  • A listed owner does not see the initial workspace. The address must match BOOTSTRAP_OWNER_EMAIL exactly (case does not matter) and be verified. After changing the secret, they sign out and in again: the new session adds them as Owner (packages/db/src/workspaces.ts:55).

Connect GitHub fails

The callback sends the browser back to the dashboard with a github_error reason, and the dashboard shows a sentence for each (apps/web/app/page.tsx:111):

ReasonFix
installation_invalidThe state cookie was missing or did not match, or installation_id was not a number. Start Connect GitHub again from the same tab and origin.
authorization_missingGitHub sent no code: turn on "Request user authorization (OAuth) during installation".
installation_not_yoursThe installer is not the installation's own account or an admin of its organization.
org_permission_missingGitHub refused the organization membership check: grant Organization permissions, Members, Read-only.
installation_failedAnything else, usually a wrong GITHUB_APP_CLIENT_ID or GITHUB_APP_CLIENT_SECRET, or D1 being unavailable. Check wrangler tail.

A site's log token leaked

The log endpoint /api/logs/<siteId> is public and trusts whoever holds the site's token. Until a site rotates it, the token is derived from SESSION_SECRET; after that, only the stored token works (apps/web/src/crawl-logs.ts:23).

  1. In Setup, under Server or CDN logs, press Rotate token (Owner or Member). It stores a new random token and the old one stops working at once (apps/web/app/api/sites/[siteId]/connectors/route.ts:53).
  2. Copy the new snippet into the log shipper (Logpush job, Vercel drain or forwarding Worker). Deliveries are refused with 401 until it is updated.

Rotating one site does not touch the others. Changing SESSION_SECRET changes every unrotated site's token at once, so rotate the leaked site instead.

Cancel a run when D1 is unavailable

The cancel route reads D1 before it terminates anything: first to check your access to the analysis's site, then to load the analysis (apps/web/app/api/analyses/[analysisId]/cancel/route.ts:9). So while D1 is over its limit Cancel returns 500 and the Workflow keeps running and spending. Stop it directly:

npx wrangler workflows instances terminate site-analysis <analysisId>

The analysis record still says running afterwards. Once D1 is back, press Cancel (or POST /api/analyses/<id>/cancel with your session cookie and Origin header): the terminate call inside it fails quietly because the instance is gone, and the record is closed as cancelled. The same works for search-sync and dataset-scrape instances.
