Glossary

The words this codebase uses, rendered from CONTEXT.md at the repository root. Short definitions of the domain terms that name modules and seams. Architecture reviews read this first; keep it to terms that would otherwise be ambiguous.

The design system is apps/web/DESIGN.md; the reasoning behind individual features is in docs/superpowers/specs/.

Performance

Results
the synced numbers (Search Console, GA4, speed, authority, keywords). Their sections (results/sections.tsx) sit in the Dashboard's tabs: the proof (clicks since go-live, the key numbers) on Overview, then Search, Enquiries, Technical (speed), Keywords and Competitors (authority). The page once called Performance (view key results, still used in file and route names) is now those tabs; old links redirect. The read-only client link (/r/<token>) stacks every section into one report, without site health.
Page results (view performance)
the landing page engine's steps 6–7, how each generated page performs. Formerly Page performance.
Ledger
metric_points, one value per site, metric and day. Numbers over time live here, and every ratio is derived by the reader. Upserts overwrite, so re-runs and Google's revised days never double count.
Metric group (METRICS in packages/core/src/results.ts)
the ledger metrics one upstream connection writes. A group is what its sync may write, what the view reads, and what a changed property clears.
Marker
a sync.* metric a source writes after each run. Its absence means a first run, which backfills history.
Snapshot (site_snapshots, packages/db/src/snapshots.ts)
a "latest list" that replaces itself, keyed by kind and scope: top_queries (property|markets), keywords (property|market: the site's Search Console queries priced by DataForSEO), competitor_keywords (domain|market: a domain's ranked keywords). The scope names what made the list, so a changed property, market or competitor hides the old list until the next sync. Counts derived from a list (kw_top10, kw_traffic) go in the ledger so they trend.
Keyword gap
a competitor's ranked keyword the site appears for in none of its lists; the best-placed competitor stands for it. The Keywords card shows the 25 biggest; the growth plan turns the reachable ones (volume ≥ 100, difficulty ≤ 40) into keyword_gap opportunities.

AI visibility

AI agent (packages/core/src/ai-agents.ts)
a user agent that reads pages for an AI company, mapped to an engine (the radar's axes: OpenAI, Anthropic, Perplexity, Meta, Common Crawl, others). A crawler collects pages ahead of time (training or an AI search index); a live fetch is an assistant opening a page to answer someone. Google has no AI user agent: its AI answers fetch as Googlebot, and Google-Extended is a robots.txt token only.
AI fetch
an AI agent's request for a published Eumon page, counted per page, day and agent in ai_page_daily (signal fetch) and rolled into ai_crawler_fetches.<engine> / ai_live_fetches.<engine>. Only Eumon's pages are seen; the rest of the client's site isn't.
AI referral
a visit an AI assistant sent, from the referrer host or utm_source (signal referral, ai_referral_visits.<assistant>). The whole site's AI-referred sessions come from GA4 (ga4_ai_sessions); the two are never added.
Landing source
where a session first landed from (search, ai:<assistant>, other), kept on page_sessions.source; it splits Eumon-page leads (leads_eumon.<source>).
Question search
a query phrased as a question (QUESTION_QUERY_PATTERN), counted from the 28-day query list the sync already fetches.
AI readiness
an analysis's robots.txt verdict per AI token (exact token match), llms.txt, Q&A markup, and the probe: how a firewall answered each AI agent that robots.txt allows. Blocking in robots.txt is reported, never scored and never auto-fixed.

Audit

Check (packages/core/src/checks/catalog.ts)
one entry in the registry: an id that is never renamed, its pillars, finding category, class, scope, sources, fix kind and docs. Every finding names its check (checkId). The Checks page is generated from the registry.
Pillar
SEO or AI visibility: which health score a check counts toward. A check can be in both; conversion and data checks are in neither.
Class
error, warning or notice. Only error-class page checks make a page unhealthy for the score; severity, set per finding, ranks the growth plan.
Health score (healthScore)
per pillar, the share of indexable crawled pages with no error-class issue, 0 to 100; zero when a site-wide error of the pillar stands; empty without a full crawl. Written to the ledger as health_seo and health_ai.
Audit table (report.audit.checks)
every registered check as passed, failed (with its page count) or skipped (with what the site lacks, or "run a full crawl once after deploying" for crawl rows older than the checks).

Sync

Source (apps/web/src/results-sources.ts)
one thing the sync collects: Search Console daily series, rankings, top queries, URL inspection, GA4, CrUX, PageSpeed, Open PageRank, the site's own numbers. Each knows its upstream, its cadence and its points. Adding a feed means adding a source, not editing the runner.
Sync runner (syncResults in apps/web/src/results-sync.ts)
runs every source for one site, connecting Google once, writing points and markers, turning a throw into a <name> failed note. The workflow calls it in each site's sources step; URL inspection is not a source but the steps after it.
Sync run (sync_runs, packages/db/src/activity.ts)
one sync and every note its sources wrote, kept 30 per site and shown in Setup → Sync history. A note with "failed", "stopped" or "refused" is a problem; Sync now on the Dashboard repeats those.
Inspection step (apps/web/src/sync-steps.ts, url-inspection.ts)
URL inspections run as Workflow steps of 40, ten asked at a time, under the Free plan's 50 subrequests a step: up to 100 Eumon pages in three steps (pages-n; a page Google fails on is recorded as checked with no verdict, so it is not asked again that day), the day's pages_indexed counts, then the day's sitemap queue read once (coverage-queue, up to 1,880 URLs) and inspected 40 a step (coverage-n). Quota ledger: the start step counts inspections already made since midnight Pacific (Google's quota day) and the run spends only what is left of 2,000. A refusal ends the site's steps for the day; a step that dies after its retries costs its note, never the run.
Daily trigger
a Worker Cron Trigger (triggers.scheduled in apps/web/cloudflare.config.ts, 04:15 UTC; Cron Triggers are on the Free plan, Workflow schedules are not) runs scheduled in worker.ts, which creates one instance per site, daily-<day>-<site> (so each has its own 1,024 steps, and a second firing creates none). "Sync now" creates manual-<site>-<ten-minute window>: clicks within the window join one run, and a manual sync is refused (409) while the site's daily run is going. The dashboard waits, up to fifteen minutes, for a manual run recorded after the window's start, and stops early when the instance errored.
Refusal
a URL Inspection answer that holds for the rest of the day: quota (429), a revoked token (401), or a whole batch of 403. A lone failure is one URL Google won't inspect; the queue moves past it.
Fresh list
a keyword list (snapshot) is refreshed when it is missing or 28 or more days old; a sync whose lists are all fresh spends nothing at DataForSEO. Budget: up to (competitors + 1) × markets calls per sync, in sequence, against the Workers Free plan's 50 subrequests per invocation.

Growth plan

Opportunity
a prioritised thing to do, from search data, competitor content, collected datasets or a technical finding. Its searchDemand and estimatedDifficulty come from one demand estimate (packages/agents/src/demand.ts); until keyword data is synced they are heuristics, and the rationales say so.
Finding key
the same problem across analyses: a finding's category and title with numbers blanked (findingKey). Each finished analysis saves its key list (kind finding_keys in the snapshot store, scope = the analysis id); a vanished row in a list says a previous finding is gone because every page it pointed at was missing or erroring in that crawl, decided on save because crawl rows are pruned later.
Resolution
a finding key present in one analysis and absent from the next (resolutions). The History tab labels it Fixed with Eumon when a merged change or opened PR names a finding with that key, No longer applies when its row vanished, and Resolved otherwise. Eumon's actions (pull requests, page edits, CTA tests, publications) are listed beside them.
Search Console import
Google's Page indexing report has no API, so its exports are imported in Setup (a reason's URL list, the overview table, the chart). Imported URLs live in search_console_urls with the reason Google gave; the overview is the search_console_summary snapshot; the chart is the gsc_indexed / gsc_not_indexed metrics.
Today status
what an imported URL is now — indexable, noindex, redirect, gone, error or unchecked — from the latest crawl's row when it has one, otherwise a live check (fetched as Googlebot from the console, twenty per request). todayStatus is the rule; searchConsoleReconciliation applies it in SQL so a 20,000-URL list costs counts, not rows.
Redirect suggestion
for a gone URL, the live URL of the same page type whose slug contains every word of the dead slug (suggestRedirect); one word alone must be six characters or more.
Trend finding
a fall in a daily series the ledger holds, reported as a finding with a date and a size (findingsFromTrends): Search Console impressions against their peak week, Google's indexed count against its 90-day maximum, and Googlebot's pace (requests a day from the crawl log) against the sitemap's size. Thresholds live in TREND beside their reasons; the math is packages/core/src/trends.ts.
Soft 404
a page that answers under 400 but says it is missing (its title or first heading, in the languages the sites use), with little else on it; also any page carrying the title the site gives a URL that cannot exist (the analysis fetches one such URL first: the 404 probe). Google crawls them, indexes nothing, and comes back.
Near-duplicate
two indexable pages with the same title whose text fingerprints (simhash of the main content — <main>/<article>, or the body without nav, header, footer, aside and forms — 64 bits kept in result_json.textHash) are within 6 bits; suffixed when their URLs differ only by a trailing code with a digit in it — the same record listed twice. Reused crawl results from before these fields existed carry none of them: run a full crawl once after deploying them.
Locale split
the full-crawl findings end their summary with the count per language version (the URL's locale prefix, default for none) when the crawl has more than one; titles stay the same, so History keys do.

Data

Ownership
every table with a site_id cascades from sites, so deleting a site is DELETE FROM sites (deleteSite clears the two largest tables first). Crawl results (pages) and changes cascade from their analysis; daily page counters (page_metrics_daily, ai_page_daily) from their generated page. A new table that belongs to a site takes REFERENCES sites(id) ON DELETE CASCADE; the demo test checks nothing survives a delete. A site in turn belongs to a workspace (sites.workspace_id), without a cascade: a workspace that still has sites can't be deleted.
Crawl result (pages)
one row per analysis and URL (PRIMARY KEY (analysis_id, url)). The page type (route_family) and reuse (reused_from, the earlier analysis a result was copied from) are columns; the rest of what the crawler saw is result_json.
Google connection
one oauth_credentials row per site with provider google, covering Search Console, Analytics and Sheets (its scopes say which were granted).
Inventory (packages/pages/src/inventory.ts; datasetInventoryRows in db)
what a dataset's records say about the site's content: fill per field (grouped by language for variants like bio_en/bio_ms or Bio (EN); a lone _id key is a foreign key, not Indonesian), records listed more than once (the same name once honorifics, case and punctuation are dropped: a suspicion to review, since two people can share a name), and the records' own pages in a crawl (thin: an empty shell or under 250 characters of text; gone: 404 or 410; unreached: not crawled, or another error). URLs match across scheme, www., fragments and trailing slashes. Four queries per dataset; an analysis reads the three largest datasets against its own crawl, in its own workflow step, and findingsFromInventory makes content findings of them (50 records or more; 50 missing a field; 4 duplicate records; 10 thin pages and a twentieth of the linked ones). The card reads the latest finished crawl.
Supabase source (kind: supabase, apps/web/src/supabase-source.ts)
a table or view read through PostgREST with a read-only key you paste once (never the service-role key: it is refused), sealed in oauth_credentials under supabase:<source id> like the Google refresh token and never returned or echoed. url is the project URL, urlPattern the table. The collection workflow (Collect, or Pull now on the row) reads it a page of 1,000 rows a step, writes each page in bulk (replaceRecords: the table is the authority, a blank erases), then removes records the source gave before that a complete pull no longer has; 40 pages at most, after which the source says the table is larger. Namesakes stay apart (dr-tan-mei-2) for the inventory to show, and a table-only run skips the by-name merge.
Table rebuild
SQLite can't add a foreign key to an existing table, so a migration that changes one creates the new table, copies the rows, drops the old one and renames. A parent is replaced only after its old children are dropped: dropping a table deletes its rows, and that delete cascades into any table already pointing at it (0019_ownership_and_indexes.sql).
Crawl counters (crawl_counts)
per analysis and page type, the counts the progress view shows (pending, fetched, reused, errors, empty, …) and the first and last fetch. Each saved batch takes its rows' old counts off and puts their new counts on in the same batch; queueing recounts once (recountCrawl). Anything that edits crawl rows outside saveCrawlBatch must call recountCrawl. The latest batch's URLs are analyses.crawl_recent.
Crawl retention
when an analysis finishes, crawl rows are deleted for all but the latest two finished analyses and any run newer than the latest one (pruneCrawlResults). Every report and crawl counter stays, so history and pace are unaffected; drill-downs read only the latest crawl.
Query budget
the Workers Free plan allows 50 D1 queries per request and 5M rows read a day. A request does a fixed number of queries (never one per item; batch over json_each instead), and anything polled reads counters, not whole tables.

Leads

Reference code (packages/core/src/whatsapp.ts)
five letters and digits (no 0/O/1/I) the browser writes into a WhatsApp link's message when it is clicked ("… (ref K7M2Q)"), on Eumon's pages (the CTA) and on the main site (the tracking snippet). The click's beacon or event carries the same code, so the chat that arrives can be matched to the visit.
Lead (leads, packages/db/src/leads.ts)
one per code (or entered by hand without one). Its status moves clicked → chat → qualified → won (with a value in the site's currency, page_settings.currency), or lost. Each stage keeps when it was reached; reaching a stage fills the earlier ones, moving back clears the later ones. No phone number or message is stored.
Outcomes (wa_clicks, lead_chats, leads_qualified, customers, revenue)
leads in the ledger on the day each stage was reached, rewritten in full by every sync and every change to a lead. By page type: leads of the last 90 days by the template of the Eumon page the visitor first landed on ("Rest of the site" when they never landed on one).

Connectors beyond Google

Search results page (snapshot kind serp, scope <market>)
Google's first page for one search (DataForSEO SERP API): result types (features: AI Overview, map pack, featured snippet…), the first ten organic results, the site's place, and whether the AI Overview cites the site. The searches are the site's biggest priced queries on the first three pages, then the biggest keyword gaps; ten pages per sync, each refreshed after 28 days.
Search competitor (snapshot kind serp_competitors, scope <market>)
a domain that ranks for the site's searches (Labs serp_competitors). A suggestion is one not on the competitor list, ranking for two or more of the searches; its kind is competitor, directory (lists businesses like the site's) or platform (social, video, encyclopedias: never suggested).
Link profile (snapshot kind backlinks, scope <domain>)
a domain's live backlinks and referring domains (Backlinks API summary); ref_domains counts referring main domains. The link gap (kind link_gap, scope the first three competitors, sorted) is the sites linking to every one of them and not to the site.
Bing (bing_* metrics)
Bing Webmaster Tools' daily clicks and impressions and crawl counts, for the site's origin as verified in the key's Bing account.
IndexNow
Eumon's pages published, changed or taken down since the last submission (snapshot kind indexnow holds its moment), sent once the proxy is verified. The key is derived from SESSION_SECRET and served at <mount>/<key>.txt, so it vouches only for Eumon's pages.
Crawl log (crawl_log_daily, crawl_log_paths)
crawler requests from the site's own server or CDN logs, posted to /api/logs/<siteId> with the site's log token: derived from SESSION_SECRET until someone presses Rotate, then a random token stored in sites.log_token, and the old one stops working at once. Per day, crawler (googlebot, bingbot, an AI agent's token, or other), page type, status class and query string; plus the latest Googlebot and Bingbot request per path. A person's request is never stored. Log coverage compares an analysis's sitemap URLs with the paths Googlebot requested in 30 days.

Accounts and access

Workspace (organization, packages/db/src/workspaces.ts)
the unit that owns sites, people, limits and GitHub installations; a Better Auth organization. Every site belongs to one (sites.workspace_id). Each user may own one workspace (organizationLimit), so free limits can't be multiplied; being a Member or Client of other workspaces doesn't count. The API can't delete a workspace. A session has an active workspace, the one the dashboard shows.
Initial workspace (ws_initial)
the workspace that holds every site from before accounts, created by migration 0024 with no limits.
Role
a person's place in one workspace (member.role). Owner: everything, including inviting and removing people and workspace administration. Member: reads and writes every site in the workspace and adds sites, but can't administer the workspace. Client: reads only, and only the sites granted to them; can't see who else is in the workspace. allows (apps/web/src/access.ts:6) is the rule.
Need (read, write, admin)
what a route asks of the caller's role. Owners pass all three, members read and write, clients read.
Client site grant (site_access)
one site a client may see. A client invitation carries its sites (site_access_invites); accepting it replaces the client's grants in that workspace with the invitation's. Removing someone removes their grants.
Invitation
an offer to join a workspace with a role, for one email, accepted at /invite/<id>. While email sending is off, Setup → Members shows the link to copy and send by hand. A pending invitation counts against the members limit, and a new user with a pending invitation gets no personal workspace.
Bootstrap owner, platform admin (BOOTSTRAP_OWNER_EMAIL)
the comma-separated emails that, once verified, become owners of the initial workspace on sign-in and may use /admin. Its API answers 404 to anyone else.
Gate (apps/web/src/gate.ts)
the first check on every request, in worker.ts before any route: public paths pass (landing pages, the events and log endpoints, client links, sign-in, invitations, static files), everything else needs a session (401 for /api/, a redirect to /sign-in otherwise), and a signed-in write to /api/ must carry an Origin equal to the app's own (403). A route nobody guarded is still not public.
Route guard (apps/web/src/guard.ts)
the check each API route makes after the gate: requireSite (a site and a need), requireOwned (a dataset, template, job, analysis… resolved to its site), requireWorkspace (the active workspace), requirePlatformAdmin. A site the caller can't see answers 404, the same as a missing one; a role that can't make the change answers 403.
Free limits (FREE_LIMITS, apps/web/src/limits.ts:18)
what a workspace may do until /admin raises it: 1 site, 3 analyses, 500 scraped pages, 20 Ask questions and 10 AI runs a day, 3 people (everyone in the workspace, whatever their role, plus pending invitations), and no DataForSEO, pull requests or Sheets export. Overrides live in workspace_limits; a null number is unlimited.
Metering, charge (workspace_usage)
a daily counter per workspace and metered action, charged by charge once the route's own checks pass, just before the work; past the limit the route answers 429 and the allowance resets at midnight UTC. An analysis, collection or scope that then can't start is given back by refund. An AI run is one model-backed action: scoping, a source preview's sample extraction, template design, dedupe, title suggestions, a proposed code change.
Feature (dataForSeo, pullRequests, sheetsExport)
an on/off limit. A route that needs a feature the workspace lacks answers 403; the sync leaves the DataForSEO key out for such a workspace (keysForLimits).
GitHub installation
a GitHub App installation a workspace proved it owns (workspace_github_installations): the install callback trades GitHub's code for a user token and accepts the installation only if that user is its account, or an active admin of its organization (apps/web/src/github-install.ts:11).
