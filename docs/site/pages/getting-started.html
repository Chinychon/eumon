Getting started

From a fresh clone to the app running on localhost, signed in, with the demo site loaded and the tests passing. Local development runs entirely on Miniflare; a Cloudflare account is only needed to deploy.

Requirements

Node.js
22 or later in practice. package.json says >=20, but the db and agents tests and npm run audit import node:sqlite (packages/db/src/sqlite.ts), which Node 20 does not have.
npm
10 (packageManager in apps/web/package.json pins npm@10.9.7).
Google OAuth client
Needed to sign in, even locally: Google is the only sign-in method the app offers by default. See Sign in locally.
Cloudflare account
Not needed locally. Deploying is covered in Operations.

Install and build the packages

npm install
npm run build:packages

build:packages compiles every package under packages/ with tsc, in dependency order (package.json). The web app imports the built dist/ copies, not the sources, so a stale build shows old features and old demo data. npm run dev, npm test, npm run typecheck, npm run eval and npm run audit all run it first.

Configure .dev.vars

cp apps/web/.dev.vars.example apps/web/.dev.vars

Three settings are needed to sign in at all: GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET and BETTER_AUTH_SECRET. Set BOOTSTRAP_OWNER_EMAIL too, so you land in the initial workspace with no limits. Once you are signed in, site analysis, CSV import, page generation, publishing and analytics work with nothing else set. Each other setting below unlocks one more feature. On a deployed Worker the rule is different: every secret declared in apps/web/cloudflare.config.ts must be set, because Cloudflare has no optional secrets.

SettingWhat it unlocks
BETTER_AUTH_SECRETRequired. Signs sign-in sessions (apps/web/src/auth.ts:52). At least 32 random characters (openssl rand -hex 32), and not the same value as SESSION_SECRET.
BOOTSTRAP_OWNER_EMAILSet it to your Google address, or several separated by commas. These users become Owner of the initial workspace and can open /admin (apps/web/src/auth.ts:23). See Sign in locally.
GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRETRequired: Google sign-in (apps/web/src/auth.ts:63). The same client also runs the Google connection: Search Console, GA4 and the Sheets export, requested as one consent. Needs a Google OAuth web client with two redirect URIs, http://localhost:5174/api/auth/callback/google (sign-in) and http://localhost:5174/api/google/callback (the connection), and the Search Console API enabled. The connection also needs SESSION_SECRET and OAUTH_ENCRYPTION_KEY.
TURNSTILE_SITE_KEY, TURNSTILE_SECRET_KEYThe bot check on email sign-in, sign-up and password reset (apps/web/src/auth.ts:118). Google sign-in does not use it, and the widget only appears when email sign-in is on (apps/web/app/sign-in/SignInForm.tsx:38). apps/web/.dev.vars.example already holds Cloudflare's test keys, which always pass: 1x00000000000000000000AA and 1x0000000000000000000000000000000AA.
SESSION_SECRETAt least 32 characters (openssl rand -hex 32); shorter values are rejected (packages/core/src/tokens.ts:20). Signs the Google connection's OAuth state and client Results links (/r/<token>). Also derives each site's IndexNow key and its original server-log token, which stays valid until the site rotates it.
OAUTH_ENCRYPTION_KEYBase64url of exactly 32 random bytes (node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"). Encrypts stored Google refresh tokens with AES-GCM (apps/web/src/gsc-auth.ts:4).
GITHUB_APP_ID, GITHUB_APP_SLUG, GITHUB_APP_PRIVATE_KEYRepository analysis and the fix engine's draft pull requests (see Code fixes for the files they may touch and the App's permissions and webhook). A GitHub App with permissions Metadata read, Contents read/write, Pull requests read/write and, under Organization permissions, Members read-only. Sites without a repository work without it.
GITHUB_APP_CLIENT_ID, GITHUB_APP_CLIENT_SECRETThe same GitHub App's Client ID and a client secret (App settings, General). The install callback trades GitHub's code for a user token to prove the person installing owns the installation (apps/web/src/github-install.ts:11). Turn on Request user authorization (OAuth) during installation in the App, and set its Callback URL to http://localhost:5174/api/github/callback: with that option on, GitHub sends the installer to the Callback URL instead of the Setup URL.
GOOGLE_API_KEYReal-user speed (Chrome UX Report) and lab scores (PageSpeed Insights). A Google Cloud API key restricted to those two APIs.
OPEN_PAGERANK_KEYThe authority estimate (Open PageRank, free key).
DATAFORSEO_LOGIN, DATAFORSEO_PASSWORDDataForSEO API login and password: keyword volume and difficulty, competitor keywords, Google results pages and search competitors, and backlinks (the Backlinks API must be active on the account).
BING_WEBMASTER_API_KEYBing clicks, impressions and crawl counts. The site must be verified in the same Bing account.
DEEPSEEK_API_KEYThe language model for scoping, extraction, page copy and title suggestions. Ask Eumon only works with this key (packages/ai/src/index.ts:242).
ANTHROPIC_API_KEYClaude as the language model when no DeepSeek key is set. Not declared in apps/web/cloudflare.config.ts, so it is ignored locally until you declare it there (see the callout below).
LLM_MODELOverrides the model of whichever provider is active, for example deepseek-v4-pro. Undeclared, like ANTHROPIC_API_KEY.
EMAIL_ENABLED, EMAIL_FROM, PASSWORD_SIGNINOff by default. EMAIL_ENABLED=true adds magic-link sign-in and email verification, sent from EMAIL_FROM through the EMAIL binding; PASSWORD_SIGNIN=true adds email and password, and only works with email on (apps/web/src/auth.ts:26). Until then, every email is written to the log instead (apps/web/src/auth.ts:31). Undeclared, like ANTHROPIC_API_KEY, so uncommenting them in .dev.vars does nothing until you declare them.

Two bindings in the config are not settings, but the sign-in flow uses them. EMAIL is Cloudflare's send-email binding; sending to any address needs Workers Paid (apps/web/cloudflare.config.ts:75). AUTH_RATE_LIMIT allows 10 sign-in attempts a minute per IP address: every non-GET request to /api/auth/* counts (apps/web/worker.ts:35). Neither needs anything in .dev.vars.

One more setting is read by the config file itself rather than the Worker: CF_D1_DATABASE_ID, an environment variable that points the DB binding at your own D1 database when you deploy a copy. It defaults to the project's database ID and does nothing locally.

Only bindings declared in apps/web/cloudflare.config.ts reach the Worker. A .dev.vars entry that is not declared there is silently ignored. ANTHROPIC_API_KEY, LLM_MODEL, EMAIL_ENABLED, EMAIL_FROM and PASSWORD_SIGNIN are left undeclared on purpose so a deploy does not require them; to use one locally, add it to the env block, for example ANTHROPIC_API_KEY: bindings.secret(). Restart the dev server after changing either file.

Which language model runs

createLlm in packages/ai/src/index.ts:50 picks the first available provider:

  1. DEEPSEEK_API_KEY, default model deepseek-flash.
  2. ANTHROPIC_API_KEY, default model claude-opus-5-5.
  3. The Workers AI binding AI, default model @cf/google/gemma-4-26b-a4b-it.

LLM_MODEL replaces the default model of the chosen provider. Scoping, extraction, page copy, title suggestions and Ask Eumon need a model; every other step works without one.

Workers AI does not work locally. apps/web/vite.config.ts sets remoteBindings: false, and the AI binding needs to run remotely. Set DEEPSEEK_API_KEY to use the AI steps in local development.

Apply the local migrations

npm run db:migrate:local

This runs cf d1 migrations apply … --local --persist-to ./.cloudflare/state in apps/web against the SQL files in packages/db/migrations. The local database lives under apps/web/.cloudflare/state. You rarely need to run it by hand: npm run dev applies any pending migration first.

Start the dev server

npm run dev

Run it from the repository root or from apps/web. It serves http://localhost:5174 with --strictPort, so it fails rather than moving to another port. Before Vite starts, apps/web/scripts/predev.mjs runs:

  1. npm run build:packages, stopping if the build fails.
  2. A check of the local D1 file for migrations it has not applied (read with node:sqlite; on Node 20 it cannot read the file and just runs the migrate command).
  3. npm run db:migrate:local when anything is pending, killed after two minutes because the beta cf CLI sometimes prints its result and never exits. Anything still unapplied is printed with the command to run.

vinext allows one dev server per directory. A second npm run dev in the same checkout refuses to start unless VINEXT_NO_DEV_LOCK=1 is set (apps/web/node_modules/vinext/dist/cli-dev-config.js). If you need a second, isolated server, give it its own Vite config with a separate persistState path and cacheDir, so it does not share the first server's D1 state.

Local D1 runs one query at a time: it is a single SQLite file behind one Miniflare Durable Object (apps/web/.cloudflare/state/v3/d1/miniflare-D1DatabaseObject/). One slow query, such as a scan with no covering index, stalls every other request, and only a dev-server restart recovers. Check a suspect query with EXPLAIN QUERY PLAN on the SQLite file, read-only, before sending it through the server.

Sign in locally

Open http://localhost:5174. Every path except a short public list needs a session, so the first thing you see is a 303 to /sign-in?next=%2F (apps/web/src/gate.ts:26). An API call without a session gets 401 instead. The sign-in page shows one button, Continue with Google: the email form only appears when EMAIL_ENABLED is on (apps/web/app/sign-in/page.tsx:8).

Google creates the account on first use. Better Auth then runs setUpNewUser (packages/db/src/workspaces.ts:32), which puts the new user in exactly one workspace:

  • An address listed in BOOTSTRAP_OWNER_EMAIL, with a verified email (Google addresses are), joins the initial workspace ws_initial as Owner. Migration 0024 creates that workspace, moves every site that existed before accounts into it, and gives it no limits (packages/db/migrations/0024_accounts.sql:24). These users also get an Admin link to /admin.
  • Anyone with a pending invitation creates no workspace; they join the inviting one by opening the invitation link.
  • Everyone else gets a personal workspace, "<name>'s workspace", with the free limits: one site, three analyses a day, and the rest in apps/web/src/limits.ts:18.

Each new session opens in the initial workspace for listed addresses, or in the user's first workspace otherwise (packages/db/src/workspaces.ts:55). If you add your address to BOOTSTRAP_OWNER_EMAIL after signing up, restart the dev server, sign out and sign in again: the new session adds you to the initial workspace as Owner. Roles and what each can do are described in Access control.

Email is off locally, so invitation, magic-link and verification messages are never sent. Invitations are still usable: when an Owner invites someone in Setup, People, the panel shows the /invite/<id> link to copy (apps/web/app/components/MembersPanel.tsx:71). To test as a second person, open that link in a private window and sign in with another Google account.

Load the demo site

The welcome page has an Explore the demo button, and Add website has Load demo site. Both call POST /api/dev/demo-site (apps/web/app/api/dev/demo-site/route.ts), which runs seedDemoSite in packages/agents/src/demo.ts:722. The route answers on the dev server at any address, and on a production build only to requests addressed to localhost, 127.0.0.1 or ::1. It needs a session with Owner or Member rights in the active workspace, and after seeding it moves the demo site into that workspace (apps/web/app/api/dev/demo-site/route.ts:17). There is one demo site per local database, so loading it from another account moves it to that account's workspace.

Sign in with an address from BOOTSTRAP_OWNER_EMAIL for demo work. In a personal workspace the demo site does not count against the site limit when it is seeded, but it does fill that workspace's one site slot, so adding a real site is refused with 429. Each demo analysis is also charged against the three analyses a day (apps/web/app/api/sites/[siteId]/analyses/route.ts:42). The initial workspace has no limits.

It deletes and rebuilds site_demo_clinic, "Demo Dental Clinic (demo data)" at https://demo-clinic.example, a fictional dental clinic group with about 1,800 sitemap URLs across page types (dentists, treatments, clinics, prices, blog). The pages are served from memory, but the real crawler and pipeline analyse them. The seed writes:

  • markets (mys, sgp) and two competitor domains;
  • the page engine: datasets with records, templates and published pages;
  • connector data: results pages, search competitors, backlinks, the link gap, Bing and IndexNow markers;
  • two finished analyses, one a month old and one two days old, built from different versions of the site so History shows changes, with a Search Console import and a merged fix between them;
  • about 16 months of fictional Results history (Search Console, GA4, AI referrals) with growth after a go-live 80 days ago.

Analyses you start on the demo site are simulated. POST /api/sites/:siteId/analyses calls startDemoRun instead of creating a Workflow, and each poll of the progress route calls advanceDemoRun, which moves the run forward to where it would be by now: a few seconds on the sitemap, the crawl at 8 URLs a second, each competitor, then the report. Click the demo button again to reset everything.

Run the tests

npm test                              # build:packages, then every workspace's test script
npm test -w @organic-growth/db        # one workspace

Tests use node:test, no framework. Each package compiles its sources and tests with tsconfig.test.json into dist-test/, then runs node --test "dist-test/**/*.test.js". The web app runs node --test directly on app/**/*.test.ts and src/**/*.test.ts. Database tests run against an in-memory SQLite database through packages/db/src/sqlite.ts, not Miniflare.

Typecheck and build

npm run typecheck   # build:packages, then tsc --noEmit in every workspace
npm run build       # build:packages, then the production Worker bundle (vite build)

The web app's typecheck first runs cf workers types -q, which generates the Worker binding types from apps/web/cloudflare.config.ts.

The eval and audit CLIs

npm run eval

The eval in evals/ runs the real collection pipeline (list discovery with pagination, extraction with the configured model, merging repeated mentions, duplicate resolution) against a public directory site, then grades it against an answer key parsed from the same pages without AI. It reports entity precision, claim precision and claim recall, and exits with status 1 below the thresholds (0.95, 0.98, 0.9). Run it before and after changing extraction prompts or merge logic.

It needs DEEPSEEK_API_KEY or ANTHROPIC_API_KEY, from the environment or read directly from apps/web/.dev.vars (so the declaration rule above does not apply). A run makes about 30 model calls, a few US cents, and fetches about 30 public pages.

npm run audit

npm run audit -- https://example.com [--max 500] [--competitor other.com] [--market idn] [--json]

scripts/audit-site.mjs runs the same steps as SiteAnalysisWorkflow (sitemap, robots.txt, a Googlebot crawl of up to --max sitemap URLs, default 500, coverage, sampled checks, findings, growth plan) with an in-memory SQLite database in place of D1. --competitor and --market repeat; --json prints the full report. Fetches go to the live site, so keep --max modest on sites you do not own.

  • A model key in the environment (not .dev.vars) lets it match competitor content types and write the plan narrative; without one, competitor sections are matched by URL name.
  • With Playwright installed (npm i -D playwright), it renders pages in Chromium for the source-versus-render comparison; otherwise that check is skipped.
  • Behind an HTTPS proxy, run it with NODE_USE_ENV_PROXY=1.
