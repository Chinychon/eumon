Eumon overview

What Eumon does, who uses it, and how the monorepo is laid out. Read this first, then follow the pointers at the bottom.

What Eumon is

Eumon is an organic growth engine for businesses of any size, from a single-location business to a large company running many sites. It has two halves that share one site record, one database and one dashboard.

Site analysis, Results and History

Given only a website URL, Eumon analyses the site the way Google sees it. The analysis Workflow (SiteAnalysisWorkflow, apps/web/src/analysis-workflow.ts) reads the sitemap and robots.txt, fetches every sitemap URL as Googlebot, groups the results by page type, compares the server HTML with what a browser renders, and turns all of that into ranked technical findings and a growth plan of prioritised opportunities. Competitors you name are compared by the kinds of pages they publish. When a GitHub repository is connected, Eumon inspects the code per route and can propose fixes as draft pull requests.

Around the analysis sit two longer-running views:

  • Results: numbers synced once a day per site by SearchSyncWorkflow (Search Console, GA4, URL inspection, speed, authority, keywords, and optional connectors such as DataForSEO and Bing). They are stored as one value per site, metric and day in the metric_points ledger. See the sync flow.
  • History: each finished analysis saves the keys of its findings, so the next one can say which problems were resolved, and whether a Eumon change (a merged pull request, a page edit) did it.

The landing-page engine

The core of the product is a programmatic landing-page engine. It breaks a business into the things people search for (doctors, procedures, malls, products), collects structured facts for each, and publishes one crawlable page per unit on the business's own domain:

Scope → Find sources → Collect → Generate → Serve on your domain → Measure → Optimize
  • Scope: an AI analyst reads the site, its sitemap and Search Console queries, and proposes datasets with fields to collect.
  • Collect: ScrapeWorkflow pulls records from the site's own pages, directories, sitemaps, a CSV import, or a Supabase table. The collector identifies as EumonBot and obeys robots.txt.
  • Generate: a template turns each record into a page. The model writes copy patterns once per template, pages are filled from data, and thin or duplicate pages are held back.
  • Serve: complete HTML at /p/:siteId/*, reached through one proxy rule on the customer's site (for example /guides).
  • Measure and optimize: page views, CTA clicks, Googlebot fetches, Search Console data per page, and leads attributed to the page a visitor first landed on.

The full pipeline is on the landing-page flow page.

Accounts and roles

Everyone who uses the dashboard signs in. Each user belongs to a workspace, and every site belongs to one workspace. A new user gets a workspace of their own at first sign-in, unless an invitation is waiting for their email address (packages/db/src/workspaces.ts:32). An Owner invites other people into the workspace as Members or Clients.

RoleSeesCan
OwnerEvery site in the workspaceEverything a Member can, plus invite and remove people.
MemberEvery site in the workspaceRead and change every site: analyse it, connect data sources, collect data, publish pages. Add sites, within the workspace's limits.
ClientOnly the sites an Owner granted themRead only. The dashboard shows them Dashboard, Landing pages and Page results (apps/web/app/page.tsx:132), and the API refuses every change.

The rule behind the table is one function, allows (apps/web/src/access.ts:6): Owners may do anything, Members anything except workspace administration, Clients only read.

  • Sign-in is with Google. Magic links and email with password are built but ship switched off, because they need email sending (apps/web/src/auth.ts:26).
  • Limits: each workspace has a site count and daily allowances (analyses, scraped pages, Ask questions, AI runs). The people listed as admins raise them per workspace on the /admin page.
  • Read-only client links still exist: /r/<token> is a signed, revocable token that shows a site's Results as one report to anyone holding the link, with no account.

Access is enforced inside the app. A request gate checks for a session before any route runs, and every API route checks the caller's role on the site it touches. Details: Web app: access control and Architecture: how a request flows.

The engine stays generic: nothing about any one business or industry is hard-coded. Datasets, fields and page ideas come from each site's own pages and search data.

Monorepo map

An npm workspace (package.json) with one app and eight packages. The packages compile with tsc to dist/, and the web app imports those built copies.

WorkspaceJob
apps/webThe Cloudflare Worker: dashboard, API routes, public landing pages, the client link, and the three Workflows.
packages/coreShared types and pure helpers used by every other package: IDs, signed tokens, metric definitions, trends, text fingerprints, WhatsApp reference codes.
packages/aiOne JSON-output interface over DeepSeek, Claude and Workers AI.
packages/dbD1 queries and the SQL migrations, plus a node:sqlite adapter for tests and the CLIs.
packages/crawlerSitemap discovery, Googlebot crawling, rendering checks and technical SEO findings.
packages/scraperThe scoping analyst, robots.txt-aware collection, structured extraction and CSV import.
packages/pagesPage generation with quality gates, HTML rendering, CTA testing and performance insights.
packages/repo-analyzerStack detection and per-route code inspection of a connected repository.
packages/agentsThe analysis pipeline, growth plan, search and competitor analysis, connector clients (Search Console, GA4, DataForSEO, Bing), pull request generation, and the demo site.

Outside the workspaces: evals/ (a collection quality eval) and scripts/audit-site.mjs (site analysis from the command line). Both are covered in Getting started.
