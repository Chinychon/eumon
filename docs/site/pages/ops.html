How code reaches production

There is no wrangler.toml or wrangler.jsonc in the repo. The Worker is described in apps/web/cloudflare.config.ts with cf/config, and deployed by the cf CLI through vinext-cloudflare deploy (the deploy script in apps/web/package.json).

Production deploys through Cloudflare Workers Builds, connected to the GitHub repository. A merge to main starts a build. The two commands configured in the Worker's Settings, Builds section are:

SettingValueWhy
Build commandnpm run buildThe root script builds every package under packages/*, then the web app (package.json).
Deploy commandnpm run deploy -w @organic-growth/web -- --skip-buildRuns vinext-cloudflare deploy inside apps/web, skipping the build that already ran. It reads the CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID that Workers Builds injects.

The default deploy command, npx wrangler deploy at the repo root, fails with "The Cloudflare application detection logic has been run in the root of a workspace instead of targeting a specific project." Wrangler finds no config at the root, and the app is not a wrangler project anyway. Keep the deploy command above.

A Workers Builds deploy runs in strict mode. If someone changed the Worker in the Cloudflare dashboard and its settings now differ from cloudflare.config.ts (a plain-text variable where the config declares a secret, for example), the deploy stops with "Aborting the upload operation because of conflicts". Keep settings in the config and secrets as Secrets, never in the dashboard (apps/web/README.md).

The Worker's name appears three more times in the config: as the worker of each Workflow binding (ANALYSIS_WORKFLOW, SCRAPE_WORKFLOW, SEARCH_SYNC_WORKFLOW). Renaming the Worker means changing all four, or the deploy fails on the name.

Builds for Preview branches

A new Worker has Builds for Preview branches switched on under Settings, Builds. With it on, every push to a branch other than main runs the Preview command npx wrangler preview, which stops with "Your Wrangler configuration is missing a previews block". The result is a failing "Workers Builds: eumon" check on every pull request. defineWorker in cf/config has no previews option, and a preview would need its own D1, AI, Browser, Workflow bindings and secrets in any case. Turn the toggle off; builds of main are not affected.

Deploying by hand

From the repository root, after npm exec -w @organic-growth/web -- cf auth login (or with CLOUDFLARE_API_TOKEN exported):

npm run db:migrate:remote   # only if packages/db/migrations gained a file
npm run deploy              # builds the packages, then vinext-cloudflare deploy

To deploy your own copy, set CF_D1_DATABASE_ID to your database and change the ID in the two db:migrate:* scripts in apps/web/package.json.

Remote migrations

Workers Builds does not apply migrations. Whoever merges a pull request that adds a file to packages/db/migrations runs this before (or with) the deploy:

npm run db:migrate:remote

It runs cf d1 migrations apply 591e4045-cbff-4ef4-a894-cbe4ece424ec --dir ../../packages/db/migrations from apps/web. Applied migrations are recorded in the d1_migrations table and skipped on the next run. Code that reads a new table or column fails in production until its migration has run, so apply first, then deploy.

To see which migrations production has not applied yet, use the same cf form (it takes the database ID, not the name):

cd apps/web
npx cf d1 migrations list 591e4045-cbff-4ef4-a894-cbe4ece424ec --dir ../../packages/db/migrations

wrangler d1 migrations list eumon-prod --remote does not work here: wrangler reads the database's migrations_dir from a wrangler config with a d1_databases entry, and the repo has none. Use the cf command above, or query the table directly: npx wrangler d1 execute eumon-prod --remote --command "SELECT name, applied_at FROM d1_migrations ORDER BY id".

Some migrations drop tables (0009_drop_unused_tables.sql) or move data (0016_site_snapshots.sql). A dropped production table cannot be restored by re-running anything. Read a migration before applying it remotely.

Schema and table descriptions live on Data model.

Secrets

Every value the Worker reads besides its bindings is declared with bindings.secret() in apps/web/cloudflare.config.ts. Cloudflare has no optional secrets: each declared secret must exist on the Worker before a deploy, even for features you do not use.

ANTHROPIC_API_KEY and LLM_MODEL are deliberately left undeclared so they stay optional; set them on the Worker directly. The provider order (DeepSeek, then Claude, then Workers AI) is described in Packages.

npx wrangler secret put SESSION_SECRET --name eumon      # prompts for the value
npx wrangler secret list --name eumon
# or, with the cf CLI installed in apps/web:
npx cf workers secrets update SESSION_SECRET --worker eumon --text '...'
npx cf workers secrets list --worker eumon

Adding a new bindings.secret() to the config means setting it on the production Worker before the next merge to main, or that deploy fails.

The cron trigger

The daily Results sync is a Worker Cron Trigger, triggers.scheduled({ schedule: "15 4 * * *" }) (apps/web/cloudflare.config.ts:10). At 04:15 UTC Cloudflare calls scheduled in apps/web/worker.ts:14, which runs startDailySyncs (apps/web/src/sync-steps.ts:208): one search-sync Workflow instance per site, with the ID daily-<YYYY-MM-DD>-<siteId>. Because the ID is fixed for the day, a second firing creates nothing. "Sync now" creates manual-<siteId>-<window> instances through POST /api/sites/<siteId>/results/sync; clicks within ten minutes join one run, and a click while that day's daily run is in flight gets a 409.

Workflow schedules are not used because they need the paid plan; cron triggers are accepted on Free. The sync itself is described in the sync flow.

Observability

Wrangler is not a dependency of this repo; npx wrangler fetches it, and npx wrangler login signs in. None of the commands below need a wrangler config: each names the Worker, Workflow or database.

Live logs

npx wrangler tail eumon --format json

Streams every request, cron firing and Workflow step invocation with its console output, exceptions and outcome (for example exceededCpu). Use --format pretty for a quick look; JSON keeps the full exception text.

Workflows

npx wrangler workflows list
npx wrangler workflows instances list site-analysis
npx wrangler workflows instances describe site-analysis <instance-id>

describe shows every step with its start and end time, retries, output and error. It is the quickest way to see which batch a crawl stopped on and with what message. Instance IDs:

WorkflowInstance IDCreated by
site-analysisThe analysis ID (analysis_…)apps/web/app/api/sites/[siteId]/analyses/route.ts:50
dataset-scrapeThe scrape job IDapps/web/app/api/datasets/[datasetId]/scrape/route.ts:24
search-syncdaily-<day>-<siteId> or manual-<siteId>-<window>apps/web/src/sync-steps.ts:187

Analysis steps are named load-site, enqueue-full-crawl, crawl-batch-<n>, research-<domain>, inventory, analyze-repository-and-site and so on (apps/web/src/analysis-workflow.ts; walkthrough in the analysis flow).

D1 usage

npx wrangler d1 info eumon-prod
npx wrangler d1 insights eumon-prod --sort-by reads --timePeriod 1d --json

d1 info prints the database size and the rows read and written in the last 24 hours: compare those with the Free plan's daily limits before starting a large crawl. d1 insights lists queries with their total and average rows read, so a query that walks a whole table stands out at the top.

An analysis's own view

curl -s https://eumon.chin-gabriel.workers.dev/api/analyses/<analysisId>/progress

Returns status, the stage timeline in progress, error, crawl counts with pace and time left in crawl, and stalled (apps/web/app/api/analyses/[analysisId]/progress/route.ts). stalled becomes true when a queued or running analysis has not updated its progress for 45 minutes (packages/db/src/index.ts:206); the dashboard then lets a new run start. If the hostname is behind Cloudflare Access, add the Access headers or use the browser.

Sync results are recorded per run: GET /api/sites/<siteId>/sync-runs returns the last 20 with each source's notes (Setup, Sync history in the dashboard). GET /api/sites/<siteId>/results/sync?id=<instance-id> returns a sync instance's Workflow status and error.

Runbook

An analysis looks stuck

  1. Read /api/analyses/<id>/progress. Note the last stage, progress.updatedAt, and stalled.
  2. Run npx wrangler workflows instances describe site-analysis <id>. If the instance is errored or terminated while the record says running, the Workflow died without closing the record: its catch block writes failed to D1 (apps/web/src/analysis-workflow.ts:207), and that write fails when D1 is unavailable or the invocation has used up its Cloudflare API calls.
  3. If the instance is still running, look at the current crawl-batch-<n> step's retries and error, and at wrangler tail for exceptions.
  4. Close the record with Cancel in the dashboard, or POST /api/analyses/<id>/cancel. Cancel terminates the instance if it still exists and marks the analysis cancelled.

Every route returns 500

  1. Check whether the routes that fail are the ones that touch D1. Static assets and pages that do not query still load.
  2. Run npx wrangler d1 info eumon-prod. If rows read in the last 24 hours are near 5 million (or rows written near 100,000), the D1 Free daily limit has been hit. Nothing in the app is broken: D1 refuses queries until the limit resets at 00:00 UTC.
  3. Find what spent the budget with npx wrangler d1 insights eumon-prod --sort-by reads --timePeriod 1d --json, and fix that query before the next large run (see Query-plan traps).
  4. If D1 is fine, npx wrangler tail eumon --format json and reload a failing page to read the exception.

A sync failed

  1. Read Setup, Sync history (or GET /api/sites/<siteId>/sync-runs). Each run lists one note per source; a failing source says why.
  2. If the run never landed there, find the instance: npx wrangler workflows instances list search-sync, then npx wrangler workflows instances describe search-sync daily-<day>-<siteId>. Read the failed step's error; "Too many subrequests" is the Free plan's 50-subrequest cap.
  3. A quota: note reports how much of Google's URL Inspection quota (2,000 per property per Pacific day, apps/web/src/sync-steps.ts:37) was already spent that day. When it is spent, inspections wait for the next Pacific day.
  4. Start a new run with Sync now. A click while that day's daily run is in flight returns 409; wait for it.

Cancel a run when D1 is unavailable

The cancel route reads the analysis from D1 before it terminates anything (apps/web/app/api/analyses/[analysisId]/cancel/route.ts), so while D1 is over its limit Cancel returns 500 and the Workflow keeps running and spending. Stop it directly:

npx wrangler workflows instances terminate site-analysis <analysisId>

The analysis record still says running afterwards. Once D1 is back, press Cancel (or POST /api/analyses/<id>/cancel): the terminate call inside it fails quietly because the instance is gone, and the record is closed as cancelled. The same works for search-sync and dataset-scrape instances.
